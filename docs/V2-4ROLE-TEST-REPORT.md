## 三、你最关心的：后台与小程序到底同不同步？

### 结论先行

> **数据层是同一份，展示层不同步。**
> 后台和小程序调的是**同一套后端接口**（`/api/{模块}`）、**同一个 `warehouse_id=2`**，
> 实测逐字段 **0 差异**。你之所以感觉「没同步」，根因是**后台前端没跟上 V2**。

### 证据 1：同一批数据，两端取，完全一致

用**老板账号**和**管理员账号**分别拉成品仓（`warehouse_id=2`）：

```
老板   : total=149  sum_stock=74  sum_value=2465.43
管理员 : total=149  sum_stock=74  sum_value=2465.43
逐 ID 库存值不一致的物料条数：0
```

仓管员赵六另外做了一次**全量逐条比对**：

| 仓库 | 后台 total | 小程序 total | 仅后台有 | 仅小程序有 | 库存不一致条数 |
|---|---|---|---|---|---|
| 配件仓(id=1) | 1770 | 1770 | 0 | 0 | **0** |
| 成品仓(id=2) | 149 | 149 | 0 | 0 | **0** |

### 证据 2：后台的「成品仓」不是第二套数据源

后台菜单写死了 `warehouseCode: 'chengpin'`，看起来像独立配置，实际查证：

- `chengpin` **只用于展示**（决定细分类叫「车间」、隐藏「编号」列）
- 取数时先按 code 反查仓库拿到 `_id=2`，再调 `materialApi.list({warehouse_id:2})`
- 小程序走的是**同一个** `material.list{warehouse_id:2}`

→ `chengpin` 只是「点哪个菜单 → 查哪个 warehouse_id」的映射表，**不是另一套数据源**。

### 证据 3：真正的「不同步」在这里（共 4 处，已全部修复）

| # | 问题 | 现象 | 状态 |
|---|---|---|---|
| 1 | **后台产物是旧的** | `admin/dist` 构建于 10-01，落后源码 2 天，里面还残留已废弃的「入库员」角色 | ✅ 已重建 |
| 2 | **后台看板状态文案缺 V2 三态** | **同一张单，小程序显示「待收货」，后台看板显示英文 `receiving`** ← 这最像你说的「不同步」 | ✅ 已修 |
| 3 | 后台统计页状态文案同样缺三态 | 同上，且筛选项里没有「待拣货/待收货/已完成」 | ✅ 已修 |
| 4 | 后台缺「消息中心」页面 | `messageApi` 早写好了，但**没有任何页面用它**，路由和菜单都没有 | ✅ 已新建 |
| 5 | **后台首页文件被浏览器缓存 1 天** | 发版后你就算刷新，浏览器 24 小时内仍用旧 `index.html` → 看到的就是**旧版后台**（没有采购任务菜单），极端情况直接白屏 | ✅ 已修 |

另外后台看板原来只统计「待确认出库单」，**看不到「待拣货/待收货」的积压**，也已补上。

#### 第 5 条的完整因果链（这条最可能是你亲眼看到的「没同步」）

```
① 服务端给 /admin/ 下所有文件都发 Cache-Control: public, max-age=86400
   （index.html 也被缓存了 1 天）
② 我重建了 admin/dist，JS 文件名里的 hash 变了（如 index-Cx5ADIu9 → index-Dz1DMK04）
③ 你的浏览器还在用缓存里的旧 index.html，它引用的是已经不存在的旧 hash 文件
④ 请求旧文件 → 服务端的 SPA 兜底路由把 index.html 当成资源回给你
   （实测：任何不存在的 /admin/* 都返回 200 + Content-Type: text/html，连随机路径都是）
⑤ 浏览器拿 HTML 当 JS 模块解析 → 报 MIME 类型错误 → 后台白屏
```

**修法**（`server/src/app.js`，已改完并实测）：

- `index.html` 改为 `no-store, no-cache, must-revalidate, max-age=0`（每次都要校验）
- 带 hash 的静态资源**保持** `max-age=86400`（hash 变了文件名就变，长缓存是安全的）
- SPA 兜底路由识别出「请求的是静态资源」时**回 404**，不再拿 HTML 糊弄浏览器

实测结果：`/admin/index.html` 已返回 no-store；不存在的 `.js` 现在回 404（原来回 200+HTML）；
`/admin/order/purchase-tasks` 这类前端路由仍正常兜底为页面。

## 四、P0（逐条：现象 / 证据 / 独立复核 / 修复）

### P0-1 采购单价能被记成 0，且照样生成成本为 0 的入库单

**现象**（采购员李娜报）：采购录入时漏填单价、填 `0`、填 `"abc"`，**三种都能提交成功**，
金额算成 0 元，仓管收料时也不会二次校验。

**原始证据**
```
entry 不传 unit_price → {"code":0,"data":{"status":"purchased"},"message":"已提交，等待仓管收货入库"}
随后 total_amount = 0
```

**独立复核（读源码确认根因）**
`server/src/modules/purchase.js`：
```js
const p = num(it.unit_price)
if (p < 0) return fail(400, '单价不能为负数')   // ← 只拦了负数
priceMap.set(mid, p)                            // ← 0 被存进去了
...
if (!priceMap.has(Number(it.material_id))) {    // ← 于是「必须有单价」这道检查也被绕过
  return fail(400, '请填写实际单价')
}
```
**根因**：`p < 0` 应为 `p > 0`；`num()` 把 missing/非数字统一吞成 `0`，0 进 map 后 key 存在，
第二道检查形同虚设。后台前端 `tasks.vue` 的 `el-input-number :min="0"` 同样放行 0。

**影响**：采购成本可被静默记成 0 → 入库成本、库存总值全跟着错，且**仓管收料时不复核**。

**修复**：`if (!(p > 0)) return fail(400, '每一项的实际单价都必须大于 0（采购成本要按它计算）')`

---

### P0-2 老板账号可以把自己/别人提升为「管理员」（提权）

**现象**（老板王总报）：用 boss 账号调 `user.updateRole` 把任意用户设成 `admin`，成功。

**独立复核（我实测，不是照抄 Agent 结论）**
```
王总 updateRole { id: 5, roles: ["admin"] } → code=0  message=角色已更新
复核该账号当前角色 → ["admin"]   ⚠️ 提权成功
（复核后已立即改回 ["purchase"]）
```

**根因**：`user.js` 的 `updateRole` 只做了角色白名单过滤（`VALID_ROLES`）+ 两条「防止锁门」护栏，
**没有任何「不能授予高于自己角色」的校验**。而 `user.updateRole` 的 `roleRules` 是 `['boss','admin']`，
所以老板本来就能改角色 → 顺手把自己变成 admin。

**影响**：`admin` 比 `boss` 多出「作废已完成的出库单」等能力，绕过了权限边界。

**修复**：
```js
if (roles && roles.includes('admin') && !myRoles.includes('admin')) {
  return fail(403, '只有「管理员」才能授予「管理员」角色，请联系系统管理员操作')
}
```

## 七、系统做对的地方（整改时别误伤）

- **库存语义完全正确**：提交/确认/拣货**都不动库存**，只有「确认收货」才扣；
  采购只有「收料入库」才加。7 个测试物料逐笔重建，**0 差错**。
- **对账能力过关**：随机抽物料把库存流水累加 = 当前库存，全部 MATCH；能查到「谁 / 何时 / 因哪张单」。
- **异常路径是亮点**：库存不足在「提交 + 确认」双拦截并说明差多少；重复操作全幂等；
  采购退回/取消守卫齐备；**直接改库存被拦**（提示语被老板评为最佳）。
- **并发安全**：条件更新 + 事务，抢单只有一个能成功，竞争失败方拿到明确提示。
- **防冲突设计**：同一物料不能同时挂在两张未完成的盘点单里（本次测试真的撞上了，是正确行为）。
- **权限边界总体靠谱**：越权尝试基本都被 403 拦下，且按仓库收敛。

### 3. 待拣货可撤 / 待收货不可撤

### 4. 模拟库存数据（已灌入本地库）

**背景**：1919 条物料里 1906 条库存和均价都是 0 → 预警显示 1907 条、金额类报表全是 0。

**做法**（`scripts/seed-sim-stock.js`，默认预演，`--apply` 才写）：

- 只动「库存为 0 且非测试物料」的 **1906 条**，其余 13 条一条不碰
- **数量和均价一起灌**；同名物料均价一致（同名就是同一个配件，价格忽高忽低一眼就假）
- 单价越高备货越少（贵料少备、便宜料多备）——1919 种料每种都堆几十件不像真实仓库
- **数量与流水一起写**：每条补一条 `change_type='adjust'` 的流水，
  保证「流水累加 = 当前库存」这条对账链仍然成立（只改数量不写流水会直接破坏对账）

| 指标 | 灌之前 | 灌之后 |
|---|---|---|
| 有库存的物料 | 13 条 | 1908 条 |
| 预警物料 | 1907 条 | **31 条**（含缺货 11 条） |
| 库存总量 | — | 103,324 |
| 库存总值 | ¥0 | **¥6,431,330**（按估算均价） |
| 库存与流水对不上的物料 | — | **0 条**（全量校验 1919 条） |

**生产数据到位后一键还原**（原值已自动备份）：
```
node scripts/seed-sim-stock.js --restore "server/scripts/backups/sim-stock-before-2026-10-03T11-36-48-196Z.json"
```

> ⚠️ 均价是按物料名估算的**模拟值**，不是真实采购价；真实价格等生产数据录入时一并替换。

### 5. 顺手修掉的一条 P1：预警口径不一致（就是你报的那条）
