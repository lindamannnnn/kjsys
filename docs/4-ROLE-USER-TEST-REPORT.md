## 三、P0 致命问题（11 条，全部经独立验证）

> 每条都标注了**独立验证方式**：`代码` = 我读了源码确认根因；`实测` = 我实际发请求复现。

### 3.1 仓库级权限完全没生效（最严重）

**现象**：配件仓的出库员/仓管员可以操作**成品仓**的物料，并真实扣减该仓库存。单据还会被记成配件仓的。

- 证据（张三）：`outbound submit {material_id:轴承F型(成品仓), quantity:1}` → `code:0`，轴承库存 **50→49**，而张三是「可管仓库=[1] 配件仓」
- 证据（赵六）：`outbound submit {warehouse_id:2, ...}` → `code:0`，成品仓 1917 库存 **50→49**
- **独立验证（代码）**：`src/services/warehouse.js` 里定义了 `canAccessWarehouse()`，但**全项目零调用**——
  `grep -rn canAccessWarehouse src/` 只命中它自己的定义处。仓库权限是彻底的摆设。

**修复方式**：在 outbound / inbound / check / stats / material 的每个涉及仓库的动作里调用 `canAccessWarehouse`，不通过直接 403。

### 3.2 混仓下单：一单可含多个仓库的物料，单头只记第一项的仓库

- 证据（张三）：`items=[1912(配件仓), 1917(成品仓)]` → `code:0`，单据 `warehouse_name=配件仓`，明细里却含成品仓的轴承
- **独立验证（代码）**：`outbound.js:61` 单头仓库取 `data.warehouse_id || items[0].warehouse_id`，
  之后**从不校验明细是否属于该仓库**；明细本身也不记录仓库。
- 小程序 `out/pages/submit.vue:324` 用 `cartList[0].warehouse_id` 填单头 → 用户只要在购物车里混了仓，单据仓库就是错的

**修复方式**：提交时校验所有明细属同一仓库；或让明细各记自己的仓库。

### 3.3 改价接口「假失败真落库」——报 500 但数据已经改了

- 证据（李娜）：`updatePrice {id:24, unit_price:7}` → `{"code":500,"message":"total is not defined"}`；回查单据 `unit_price` 已变 7、`total_price` 已变 70
- **独立验证（代码）**：`inbound.js` 的 `updatePrice` 里 `let total = 0` 声明在**事务闭包内部**，
  而 `return ok({ total_price: money(total) })` 写在闭包**外面** → 事务已提交后抛 `ReferenceError`，
  全局错误处理返回 500。数据库已改，接口说失败。

**危害**：员工以为没改成 → 反复操作或换方式重录 → 单价被改乱且无从确认当前值。

**修复方式**：把 `total` 提到闭包外；并给 `updatePrice` 补操作日志（当前不留痕）。

### 3.4 改价忽略 material_id，把整单所有明细覆盖成同一个单价

- 证据（李娜）：只想改 D 型 → 回查整单两项**都**变成了 10.5（E 型 15→10.5，金额 2250→1575）
- **独立验证（代码）**：`updatePrice` 只读 `data.unit_price`，然后 `for (const it of items)` 无差别写入每一项，
  完全没读 `data.items[].material_id`

**修复方式**：按 `items[].material_id` 精确改指定明细。

### 3.5 改价后库存加权成本不重算 → 账面金额少计

- 证据（李娜）：单据 D 项改成 10.5 后，该物料 `avg_cost` 仍是 **9.9**；
  再入 100@11 后系统给 **10.2667**，**正确应为 10.6667** → 账面少计 **120 元**
- **独立验证（代码）**：`updatePrice` 只更新单据两张表，**完全没有触碰 `materials.avg_cost`**

**修复方式**：改价后按 `(当前库存×当前成本 + 变动数量×新单价) ÷ 总数量` 重算，并写库存流水留痕。

> 3.3 / 3.4 / 3.5 是**同一段代码的三个缺陷**，必须一起修，否则采购的账永远对不平。

### 3.6 看板「今日出库」把明细行当成单数

- 证据（王总）：看板显示 **25**，统计页显示 **23 单**（正确 23）
- **独立验证（代码）**：`stats.js` 的 `outToday` 用 `COUNT(*)` 且 `LEFT JOIN outbound_order_items`
  → 一单 2 料算 2 单。而同一个文件里的 `outMonth` 不加 join、口径正确 → **同文件两套口径打架**

**修复方式**：`COUNT(DISTINCT o.id)`。

### 3.7 看板「今日入库金额」按明细行重复累加，数值翻倍

- 证据（王总）：接口给 **¥21,059**，**正确 ¥10,024**（15 张入库单金额之和）；
  他逐单验证「Σ 单金额 × 明细行数 = 21,059」分毫不差
- **独立验证（代码）**：`inToday` 里 `COUNT(DISTINCT o.id)` 是对的，
  但 `SUM(o.total_price)` 在 `LEFT JOIN` 明细后会把主单金额**按明细行数重复求和**

**修复方式**：主单金额用子查询或先聚合主单再 join。

### 3.8 `material/import` 可携带库存无痕写入，不产生任何流水

- 证据（王总）：导入 `current_stock:500` → 库存真的变 500；该物料 `stockFlow` → `total:0`（**零流水**）
- **独立验证（代码）**：`material.js:178` 的 INSERT 直接用 `num(item.current_stock, 0)`，**不写 `stock_logs`**

**危害**：老板最痛的就是「账对不上还查不出人」，这条路没堵上，第 3 轮那套漂亮的流水就变成"防君子不防小人"。

**修复方式**：禁止 import 携带库存字段；确需初始化则必须写 `stock_logs` 且标记来源。

### 3.9 盘点「差异」与实际库存调整量不一致（仓管不敢签字的直接原因）

- 证据（赵六）：单据记 `difference:-5`，库存流水只调了 **-2.5**（90.5→88）。**同一件事两个数**
- **独立验证（代码）**：`check.js:218-223` 里 `book` 取的是 `stock_check_items.book_stock`，
  这是**建单那一刻的库存快照**；而审核时 `adjustForCheck` 是按**当时的实际库存**算调整量。
  建单到提交之间只要有人出入库，两个数就一定对不上。

**修复方式**：提交盘点时重新取当前库存作为 `book`，让「差异」= 实际调整量；不一致就报错拦下。

### 3.10 盘点实盘数可填负数 / 小数，审核后库存真的变成负数

- 证据（赵六）：`submit {actual_stock:-3}` → `code:0`；审核后 `current_stock: -3`（**库存里出现 -3 个空气滤芯**）
- 证据（张三）：出库可填 `0.5` → 实测出现 `current_stock: 89.5`（**半个火花塞**）
- **独立验证（代码）**：`format.js` 的 `qty()` 只做四舍五入，**不夹取负数也不校验整数**；
  `check.js:209` / `outbound.js:39` 都只判 `<= 0` 或不判

**修复方式**：数量必须为正整数（或按物料单位定义允许的小数位），负数一律 400。

### 3.11 老板能摘掉自己最后一个管理角色，导致全盘锁死且无法自救

- 证据（王总）：`updateRole {id:10, roles:["out"]}` 返回成功 → 随后所有管理接口 403 → **再改回来也是 403**（他已经不是 boss 了）
  最后靠 `admin` 账号才恢复
- **独立验证（代码）**：`user.js` 的 `updateRole` 只拦「取消自己的 **admin** 权限」，
  **boss 不在保护范围**（`(ctx.user.roles||[]).includes('admin')` 才拦）

**修复方式**：保护「自己的最后一个管理角色」，不只是 admin。

## 七、修复优先级建议

### 第一批：一天能修完，且直接决定"能不能用"

| 序 | 修什么 | 对应条 |
|---|---|---|
| 1 | **让仓库权限真正生效**（调用 `canAccessWarehouse`） | 3.1 |
| 2 | **修统计口径**：今日出库单数、今日入库金额 | 3.6 / 3.7 |
| 3 | **改价三连修**：作用域错误 + 按 material_id 精确改 + 同步重算加权成本 | 3.3 / 3.4 / 3.5 |
| 4 | **数量校验**：负数、小数一律拦（含盘点、出库、入库） | 3.10 |
| 5 | **保护最后一个管理角色** | 3.11 |

### 10.5 整改过程中又抓出来的两个问题（记录在案）

验证不是走过场，它自己抓出了两个东西：

**① 后端真漏字段：流水拿不到单号**

契约脚本断言「流水带 `order_no`」时失败。查下去发现：`stock_logs` 里存单号的列叫 `related_order_id`，
而新做的对账页读的是 `order_no` —— 界面那一列会**永远是空的**。
已在 `stats.stockFlow` 补 `related_order_id AS order_no` 别名（`related_order_id` 保留不变）。

**② 我自己写的断言"看着通过、其实没验到"**

原来那条「采购员可看出库单」只判了 `code === 0`。但出库单的可见范围当时**只给"本人"**，
而采购员几乎不提交出库单 → **接口返回成功、列表恒为空**，断言照样"通过"，可是对账还是缺一半。
已修：出库单列表与详情对采购开放（限其可管仓库，与 `inbound` 一致），
断言也改成**用张三提交的单号做实证**，并补了明细与详情两条。

> 教训记在这：**「接口没报错」不等于「用户能看到东西」**。涉及权限的断言必须拿"别人的单"做实证。
