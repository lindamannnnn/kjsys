# 上线前检查与发布流程

> 这份文档解决的是同一个痛点反复出现：**「测过了」但一上线用户一点就报错**。
>
> 起因：2026-10-16 生产实操，一次性暴露 3 个缺陷，全都是**同一类病**——
> 代码 / 数据库 / 部署三者不一致，而单元测试、接口冒烟、本地库**一个都抓不到**。

---

## 一、为什么之前测不出来

| 缺陷 | 现象 | 为什么原有测试抓不到 |
|---|---|---|
| 采购录价 500 | 采购员点「录入采购信息」必失败 | 代码要写 `purchase_task_items.channel_remark`，**库和 schema.sql 两边都没这列** → 漂移检测报「无漂移」。本地库是自己建的、结构是新的，所以本地跑得通 |
| 消息已读 401 | 任何账号点「标记已读」都失败 | 读端只认 `openid`，而后台手工建的账号**根本没有 openid**。本地账号恰好都有，测不出来 |
| 采购指派下拉空 | 指派采购员时选不到人 | 同上：SQL 里用「openid 非空」筛人，把后台账号整批排除 |

**共同点**：本地环境「太干净」——结构最新、账号齐备、openid 齐全。
所以本地全绿是个**假信号**。真正要保证的是三件事**同时**成立：

1. 代码里写到的每个「表.列」，**生产库**都有
2. **生产库**结构 = `schema.sql`
3. **生产跑的**就是你手上这份代码（没有漏传、没有被手工改过）

## 二、四道闸门

### ① `npm run preflight` —— 结构与口径（不需要网络）

```bash
cd server && npm run preflight
```

三个检查一起跑：

| 检查 | 判据 | 抓什么 |
|---|---|---|
| 结构漂移 | `schema.sql` ⇄ 库 | 库落后于 schema.sql（缺表/缺列/类型不一致，含 ENUM 值） |
| 代码列引用 | 代码实写的「表.列」⇄ 库 | **schema.sql 自己也漏了**的列（漂移检测的盲区） |
| 身份口径 lint | 静态扫描 | 用「openid 有无」筛人 —— 会让后台账号被整批排除 |

退出码 `0` = 全绿可上线；`1` = 有阻塞项；`2` = 闸门自身故障。

### ② `bash server/scripts/check-deploy-consistency.sh` —— 部署一致性

生产目录 `/opt/shenglong` **不是 git 仓库**，部署靠手动传文件，
所以「本地改了忘了传」「传了一半」**没有任何机制能发现**。

这个脚本逐文件比对（**去行尾 CR 后**再算哈希，避免 CRLF/LF 假警报）：

```bash
bash server/scripts/check-deploy-consistency.sh
# 换目标：
SSH_TARGET=ubuntu@1.2.3.4 REMOTE_SERVER_DIR=/opt/app/server bash server/scripts/check-deploy-consistency.sh
```

> 实测价值：2026-10-16 抓到 `migrate-outbound-4stage.js` 本地已加固、生产还是旧版
> （旧版会在已切到新流程的库上误改历史单的扣账标记，**而且改错了是静默的**）。

### ③ `npm run smoke:prod` —— 真实接口冒烟

```bash
SMOKE_TOKEN=<token> npm run smoke:prod
# 或： SMOKE_USER=admin SMOKE_PASS=*** npm run smoke:prod
# 换目标： SMOKE_BASE_URL=http://127.0.0.1:3000 SMOKE_TOKEN=*** npm run smoke:prod
```

- **只读接口**：先用 `list` 探到真实样本 id 再查 `detail`（写死 `id=1` 会假失败）
- **写接口**：只传缺参 / 不存在的 id，期望 `400/403/404`。
  **返回 500 = 未捕获异常，是缺陷**（用户会看到「系统错误」而不是「请选择物料」）
- **污染控制**：不产生业务数据。⚠️ 有副作用的接口（如 `message.markAllRead`，没有必填参数、传空也照做）**已排除**，否则脚本会一边号称零污染一边真改数据

结果落盘 `server/scripts/out/smoke-<时间>.json`。

### ④ 业务链路实操（人工，真机）

前三道闸门**都是静态或浅层调用**，覆盖不到「真下单一整条链路」。
所以正式上线前仍需按真实角色走一遍：**到货即入库 → 出库四态 → 盘点 → 采购全流程**，
并核对库存数（水鞋 10→5 这类）。写操作**必须带测试标记 + 用完自清理**。

## 三、标准流程（照着做）

```bash
# ── 第 0 步：本机确认改动
cd server && npm run preflight          # 对本地库跑，先自证

# ── 第 1 步：闸门 ① 对「生产库」跑一次（预演，不动生产文件）
#    把最新代码放到生产的独立目录，用生产库做静态对撞：
tar czf /tmp/pf.tgz src scripts package.json
scp /tmp/pf.tgz ubuntu@119.91.206.235:/tmp/
ssh ubuntu@119.91.206.235 'rm -rf /opt/shenglong/_pf && mkdir -p /opt/shenglong/_pf \
  && tar xzf /tmp/pf.tgz -C /opt/shenglong/_pf \
  && ln -sfn /opt/shenglong/server/node_modules /opt/shenglong/_pf/node_modules \
  && ln -sfn /opt/shenglong/server/.env /opt/shenglong/_pf/.env \
  && cd /opt/shenglong/_pf && /opt/node/bin/node scripts/preflight.js'

# ── 第 2 步：部署文件（备份 → 覆盖）
ssh ubuntu@119.91.206.235 'cd /opt/shenglong/server && cp -r src src.bak-$(date +%m%d-%H%M)'
#   rsync / scp 上传

# ── 第 3 步：闸门 ② 确认传全了（本地跑）
bash server/scripts/check-deploy-consistency.sh

# ── 第 4 步：重启服务并确认起来了
ssh ubuntu@119.91.206.235 'sudo systemctl restart shenglong-api && sleep 2 && systemctl is-active shenglong-api'
curl -s https://sl.ekkosys.cn/api/health     # 期望 db: connected

# ── 第 5 步：闸门 ③ 真实冒烟
SMOKE_TOKEN=<token> npm run smoke:prod
```

全绿之后才通知用户可以开始用。

## 四、每道闸门的边界（别误以为它万能）

| 闸门 | 抓得到 | **抓不到** |
|---|---|---|
| ① preflight | 结构不一致、身份口径写法 | 逻辑错误、并发问题、「数据本身没准备好」 |
| ② 一致性 | 漏传 / 手工改动 | 传上去但**服务没重启**（文件新、进程旧） |
| ③ 冒烟 | 500、接口不可用 | 界面渲染、交互、真机问题（相机/扫码/字体） |
| ④ 实操 | 全链路 + 库存数 | 高频并发、异常断电 |

## 五、决策记录

### D-01 · 盘点人员候选 `user.assignees`（`src/modules/user.js`，约 519 行）—— ✅ 已定：**保持现状（方案 A）**

2026-10-16 用户拍板。**只改注释，不改逻辑。**

- 现状：SQL 里 `openid IS NOT NULL AND openid <> ''`，只列出**有 openid 的活跃用户**
- **这是刻意设计，不是缺陷**。理由：盘点执行人必须能在**小程序**里执行 / 确认盘点，
  而小程序登录是 `WHERE openid = ?`（`src/modules/auth.js` 的 `login`），
  没有 openid 的账号**永远匹配不上**，登进去只会另建一个 pending 账号
  → 这类账号当盘点执行人没有意义，过滤掉才对。
- 前后端口径一致：`admin/src/views/check/create.vue:140` 的注释同样写明
  「后端只回『有 openid 的小程序用户』（后台账号进不了小程序，当不了执行人）」，
  下拉 placeholder 也是「选择参与盘点的小程序用户」→ 不是漏改。
- 处理：加注释说明 + 豁免标记
  `// preflight-allow: BARE-OPENID-NULL — 盘点执行人须能登录小程序执行盘点，无 openid 账号登不进`
- ⚠️ **豁免必须可见**：豁免项会连**理由**一起打印在闸门输出里。禁止静默消音 ——
  静默消音正是让缺陷藏起来的手法。

#### 生产数据核实（2026-10-16，据此定案）

| id | 账号 | 真实姓名 | 创建时间 | openid | 性质 |
|---|---|---|---|---|---|

| 41 | （无） | 文彬 | 2026-10-14 19:44 | **有** | **目前唯一真实人员**（boss + out + storekeeper） |

→ 下拉只出 1 人（文彬）= 生产真实情况。
**正规员工入场路径** = 员工先用小程序进来建号 → 后台审核并分配角色；
系统**没有**「绑定已有账号」功能（只有企业微信 `wecom_userid` 绑定），
所以后台手工建的真实员工账号在其本人登录小程序前，不会出现在这个下拉里（已知副作用，非缺陷）。
