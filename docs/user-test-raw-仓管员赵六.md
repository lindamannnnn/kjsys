# 【仓管员】赵六 · 3 轮真实使用汇报

## 使用前提

我是赵六，45 岁，配件仓仓管员（账号 `zhaoliu`，角色 `storekeeper`，可管仓库 1=配件仓）。
每天就是：车间/采购把单子递过来，我核对实物以后点确认；每月盘一次库，盘完把实际数量录进去。
我打字慢，就想要**按钮大、字清楚、别让我来回跳页面**。
我最怕的只有一件事：**系统里的数字和我实际数出来的不一样，但我不知道差在哪**——我签了字的库存数，错了是要我担责的。

本轮只用 6 个【测试】物料做操作，没碰另外 1909 条公司真实物料。
测试期间发现别的同事（张三、李娜，以及另一路并行的"赵六"）也在同时操作，凡状态与预期不符的我都先回查确认过，没当 bug 报。
**下面每一条都附了我实际发出的请求和系统原始返回**；只有一条是"推测"，我会明确标出来。
> 关于权限：盘点审核只有老板能点。为了验证"审核后库存到底会变成什么"，我请王总用他的账号帮我审了 4 张盘点单（下面会标出来）。我自己点审核是被拦的，原始响应也在。

## 第 1 轮：处理待确认单据（我每天点得最多的事）

### 操作过程

**1）登录**
```
POST /api/auth {"action":"adminLogin","data":{"username":"zhaoliu","password":"zl123456"}}
→ {"code":0,"data":{"user":{"real_name":"赵六","roles":["storekeeper"],"warehouse_ids":[1],"openid":null}}}
```

**2）看待确认数量**
```
POST /api/outbound {"action":"pendingCount"}
→ {"code":0,"data":{"count":3}}
POST /api/inbound {"action":"pendingCount"}
→ {"code":0,"data":{"count":0}}
```
> 一开始只有 2 张待确认（手册说的 OUT-001/002），我这边看到 3 张，多出的是同事张三刚提交的 `OUT-20260929-003`。**这不是 bug**，我先记下来。

**3）看待确认列表**
```
POST /api/outbound {"action":"list","data":{"status":"pending","page":1,"pageSize":50}}
→ {"code":0,"data":{"list":[
   {"order_no":"OUT-20260929-003","operator_name":"张三","warehouse_name":"配件仓",
    "remark":"维修工单 #2001","created_at":"...09:39:28","items":[{"material_name":"【测试】火花塞 A型","quantity":5}]},
   {"order_no":"OUT-20260929-002",...,"items":[{"material_name":"【测试】点火线圈 B型","quantity":6}]},
   {"order_no":"OUT-20260929-001",...,"items":[{"material_name":"【测试】火花塞 A型","quantity":10}]}],"total":3}}
```
**列表卡片上我能看到的**：单号、出/入库、提交人、提交时间、仓库名、物料名、总数量。
**我想看到但看不到的**：这个物料现在库里有多少、够不够扣。

**4）看一张单的详情（关键）**
```
POST /api/outbound {"action":"detail","data":{"id":52}}
→ {"code":0,"data":{"order_no":"OUT-20260929-001","type":"repair","operator_name":"张三",
   "remark":"维修工单 #1001：更换火花塞","status":"pending","warehouse_name":"配件仓",
   "created_at":"2026-09-29T09:37:47.000Z",
   "items":[{"material_id":1912,"material_name":"【测试】火花塞 A型","quantity":10,"unit":"个"}]}}
```
**整个响应里没有一个字段告诉我"火花塞现在还剩多少个"。** 我另外去查才看到：
```
POST /api/material {"action":"detail","data":{"id":1912}} → current_stock: 85
```
> 为什么是 85 不是手册写的 90？因为**张三提交那两笔时就各扣了 10 和 5**：90-10-5=85。这点系统做得对（提交即扣），但它没告诉我。

**5）确认一笔 + 回查库存（确认到底动没动库存？）**
```
POST /api/outbound {"action":"confirm","data":{"id":52}}  → {"code":0,"data":null,"message":"确认成功"}
POST /api/material  {"action":"detail","data":{"id":1912}} → current_stock: 85   ← 确认前也是 85
```
**结论：确认这个动作确实没改库存**，和手册说的一致。✔ 这一点是好的。

**6）重复确认同一笔**
```
POST /api/outbound {"action":"confirm","data":{"id":52}}
→ {"code":400,"data":null,"message":"只有待确认的单据可以确认（当前状态：confirmed）"}
```
拦住了 ✔，但提示里夹了个英文单词 `confirmed`。

**7）另一笔我想驳回 → 被拦**
```
POST /api/outbound {"action":"reject","data":{"id":53,"reason":"数量与工单不符，请核实"}}
→ {"code":403,"data":null,"message":"无操作权限"}
```

**8）异常单据的提示语**
```
{"action":"confirm","data":{"id":999999}} → {"code":404,...,"message":"单据不存在"}          ✔ 说人话
{"action":"confirm","data":{}}            → {"code":400,...,"message":"单据 ID 无效"}        ✔
{"action":"confirm","data":{"id":"abc"}}  → {"code":400,...,"message":"单据 ID 无效"}        ✔
{"action":"confirm","data":{"id":52}}（已完成）→ {"code":400,...,"message":"只有待确认的单据可以确认（当前状态：confirmed）"}
```

**9）"全部流水"页上还有一个"作废"按钮，我也点了**
```
POST /api/outbound {"action":"cancel","data":{"id":52}}
→ {"code":403,"data":null,"message":"该单据已确认入库/出库，仅管理员可作废"}
```

**10）顺手看全部流水，发现能看到成品仓的单**
```
POST /api/stats {"action":"orderFlow","data":{"page":1,"pageSize":100}}
→ total=7，里面有一条 {"kind":"inbound","order_no":"IN-20260929-002","warehouse_name":"成品仓","material_names":"【测试】轴承 F型"}
```
我只管配件仓，但成品仓的单据也摆在我面前。

### 遇到的问题

| 序 | 问题 | 严重度 | 证据（请求 → 响应） | 为什么干不下去 |
|---|---|---|---|---|
| 1-1 | **确认前看不到这个物料还有多少库存、够不够扣**。单据详情里根本没有库存字段，也没显示"扣完之后还剩多少"。 | P1 | `POST outbound {"action":"detail","data":{"id":52}}` → 返回只有 `items:[{material_name,quantity:10,unit:"个"}]`，无 `current_stock`。要另外查 `material.detail` 才知道是 85。 | 我签的字得对。看不到余量，我就没法判断这单该不该批，只能**退出这个页面→去"本仓库存"→搜物料名→记住数字→再回来点确认**。手册说"确认前后都回查库存"，实际就是要我自己当人肉库存表。而且我还得自己记住"提交时已经扣过了"，不然会把 85 当成"扣之前的数"。 |
| 1-2 | **「驳回」按钮对我这个岗位是死的**：小程序上明明给我画了驳回按钮，一点就报"无操作权限"。 | P1 | 界面：`miniprogram/src/pages/storekeeper/pending.vue:46-50` 渲染「驳回」；请求：`POST outbound {"action":"reject","data":{"id":53,...}}` → `{"code":403,"message":"无操作权限"}` | 单子不对（比如工单号对不上、数量看着离谱）的时候，**我没有"退回去"的办法**——要么捏着鼻子确认，要么把它挂在那儿找老板。挂着的单子库存已经被扣了（见 1-1），挂着就等于占我的账。 |
| 1-3 | **确认弹窗的文案和事实是反的**：弹窗写"库存将正式变动"，实际确认不动库存（提交时早扣完了）。 | P1 | 界面：`pending.vue:122` → `content: \`确认 ${item.order_no} 吗？库存将正式变动。\``；实测 `confirm` 前后 `current_stock` 都是 85。 | 这句话让我**对风险判断完全反了**：我会以为"不点确认库存就没动"，于是把单子挂着；也会以为"点了确认才是真扣货"。真实情况是**张三一提交，货在账上就已经没了，我确认不确认都改变不了**。我核实物的时候按这个文案去理解，账就会错。 |
| 1-4 | 「作废」按钮对我也是死的（对已确认单）。 | P2 | 界面：`orders.vue:55-59` 对 `confirmed/completed` 单据渲染「作废」；请求：`POST outbound {"action":"cancel","data":{"id":52}}` → `{"code":403,"message":"该单据已确认入库/出库，仅管理员可作废"}` | 又一个点了必报错的按钮。多点几次我就不知道哪些按钮是我能用的了。 |
| 1-5 | 提示语里夹英文状态词。 | P2 | `"只有待确认的单据可以确认（当前状态：confirmed）"` | 我高中学历，`confirmed` 这种东西看不懂，只能猜。 |
| 1-6 | 操作员列表里能看到成品仓的单据（我只管配件仓）。 | P1（并入第 3 轮 P0-6） | `POST stats {"action":"orderFlow"}` → 出现 `warehouse_name:"成品仓"` 的 `IN-20260929-002` | 不是我的活摆在我面前，我分不清哪些是我该处理的。 |

### 本轮结论

**能点完，但点得心里没底。** 确认/驳回/异常提示这些"按钮行为"本身是正常的（确认不改库存这点尤其好）。
卡在**"确认之前我手上的信息不够做判断"**：看不到余量、看不到依据、也退不回去。
手册上让我做这个岗位，可我这个岗位每天要点的第一个按钮，就是在**信息不全**的情况下签字。

## 第 2 轮：盘点（重点，也是我最在意的一轮）

### 操作过程

**1）按手册的参数建盘点单（我只想盘 2 个物料：刹车片 C型、火花塞 A型）**
```
POST /api/check {"action":"create","data":{"warehouse_id":1,"remark":"9月配件仓抽盘：刹车片C型、火花塞A型",
  "items":[{"material_id":1914,"actual_quantity":3},{"material_id":1912,"actual_quantity":90}]}}
→ {"code":500,"data":null,"message":"Duplicate entry 'CHK-20260929-001' for key 'stock_checks.uk_check_no'"}
```
**第一次建单直接 500，还把数据库的原始报错吐给我看。**

**再试一次（同样的意图）**
```
POST /api/check {"action":"create","data":{"warehouse_id":1,"remark":"再试一次","items":[{"material_id":1914,"actual_quantity":3}]}}
→ {"code":0,"data":{"_id":10,"check_no":"CHK-20260929-002","item_count":1764},"message":"盘点任务已创建，共 1764 项物料"}
```
**我只想盘 2 个物料，系统给我建了一张 1764 项的单子。** 看我填的 `items[]`——**它一个字都没用**。

**2）看这张单的内容**
```
POST /api/check {"action":"detail","data":{"id":10}}
→ 状态=pending，items 总数=1764
   前 3 项 = [{"material_name":"扒板","material_spec":"600*552*16","book_stock":0},
              {"material_name":"热板",...,"book_stock":0},
              {"material_name":"热板",...,"book_stock":0}]
   最后 1 项 = {"material_name":"【测试】空气滤芯 E型","book_stock":160}
   ← 里面全是公司真实物料！我那个 remark 也没了
```

**3）我想去列表里看看这张单 → 列表是空的**
```
POST /api/check {"action":"list","data":{"page":1,"pageSize":100}}
→ {"code":0,"data":{"list":[],"total":0,"page":1,"pageSize":100},"message":"操作成功"}
```
**我明明已经建了 3 张盘点单，列表一条都不给我。** 换成出库单列表（同一个身份）就正常：
```
POST /api/outbound {"action":"list","data":{"page":1,"pageSize":5}} → total 有数据 ✔
```

**4）换个办法把范围限定住**
```
POST /api/check {"action":"create","data":{"warehouse_id":1,"type":"sample","scope":{"material_ids":[1914,1912],"categories":[]}}}
→ {"code":0,"data":{"_id":11,"check_no":"CHK-20260929-003","item_count":2},"message":"盘点任务已创建，共 2 项物料"}
```
只有把物料塞进 `scope.material_ids` 才能限定住——**可小程序上没这个入口**：
`miniprogram/src/pages/check/list.vue:74-81` 的"新建盘点任务"只有 6 个选项：全盘/抽盘/循环盘 × 配件仓/成品仓，`scope` 永远传空数组。

**5）读这张单的账面快照 → 提交实盘（C型实物只有 2 个、火花塞实物 88 个）**
```
POST /api/check {"action":"detail","data":{"id":11}}
→ items: 火花塞 book_stock=93；刹车片C型 book_stock=10   （账面跟手册说的 3/90 不一样，因为同事刚动过货，我以系统当时的数为准）

POST /api/check {"action":"submit","data":{"id":11,"items":[
  {"material_id":1914,"actual_stock":2},{"material_id":1912,"actual_stock":88}]}}
→ {"code":0,"data":null,"message":"盘点结果已提交，等待审核"}

POST /api/check {"action":"detail","data":{"id":11}}
→ 状态=pending_review，火花塞 账=93 实=88 差=-5；C型 账=10 实=2 差=-8
   summary: {"total":2,"checked":2,"diff":2,"surplus":0,"loss":2}
```

**6）提交后库存动了吗？**
```
POST /api/material {"action":"detail","data":{"id":1914}} → current_stock: 10   ← 提交前也是 10
POST /api/material {"action":"detail","data":{"id":1912}} → current_stock: 93   ← 提交前也是 93
```
**提交盘点结果没有直接改库存** ✔ —— 这一点非常好，说明"必须有人审核才能动账"。

**7）我自己试着审核 / 取消**
```
POST /api/check {"action":"review","data":{"id":11,"approved":true}} → {"code":403,"message":"无操作权限"}
POST /api/check {"action":"cancel","data":{"id":11}}                 → {"code":403,"message":"无操作权限"}
```

**8）已提交待审的单子，我再交一次能不能改数**
```
POST /api/check {"action":"submit","data":{"id":11,"items":[{"material_id":1914,"actual_stock":99}]}}
→ {"code":0,"data":null,"message":"盘点结果已提交，等待审核"}   ← 改成功了
```

**9）填负数**
```

→ {"code":0,...,"message":"盘点结果已提交，等待审核"}
POST /api/check {"action":"detail","data":{"id":11}}

```
**负数照收。**（我在正式业务里又把数改回 2/88 了。）

**10）不存在的物料 / 重复建单**
```
POST /api/check {"action":"create","data":{"warehouse_id":1,"scope":{"material_ids":[999999]}}}
→ {"code":400,...,"message":"所选范围内没有物料，无法创建盘点任务"}   ✔ 好提示
POST /api/check {"action":"submit","data":{"id":11,"items":[{"material_id":999999,"actual_stock":1}]}}
→ {"code":0,...,"message":"盘点结果已提交，等待审核"}                 ← 不存在的物料被静默吃掉，还回成功
```

**11）请王总帮忙审核（我请的，不是我自己的权限）——按手册参数传"退回"**
```
POST /api/check {"action":"review","data":{"id":11,"approved":false,"remark":"C型差异太大，退回重盘"}}
→ {"code":0,"data":{"adjusted":2,"diff":2},"message":"审核完成，已调整 2 项差异库存"}
POST /api/check {"action":"detail","data":{"id":11}}
→ 状态=completed，审核人=王总，completed_at=……
```
**我的意思是"退回重盘"，系统给我执行成了"通过并且把库存改了"。**

**12）审核后回查库存**
```
1914 刹车片C型 10 → 2  ✔ 等于实盘数
1912 火花塞A型 93 → 88 ✔ 等于实盘数
```
**最终库存 = 我数的数**，这一步是对的 ✔。

**13）可信度自检：差异数对不对？**
```
盘点单 CHK-20260929-003 记录：火花塞 账=93 实=88 差异=-5；C型 账=10 实=2 差异=-8

库存流水（stats/stockFlow, material_id=1912）：
  ... 2026-09-29T09:42:52 | check_adjust | -2.5 | 90.5 → 88 | CHK-20260929-003 | 王总 | 盘点差异调整：账 93 → 实 88
```
**盘点单说差了 5 个，实际库存只调了 2.5 个，中间备注还写着"账 93"。**

**14）顺手发现：库存里出现了"半个火花塞"**
```
同一张流水：2026-09-29T09:42:32 | outbound | -0.5 | 92 → 91.5 | OUT-20260929-006 | 张三 | 测试小数
最终库存：1912 【测试】火花塞 A型 库存=89.5
```
火花塞单位是"个"，系统里出现了 89.5 个、91.5 个。

**15）同一物料上有好几张盘点单同时挂着（我离开时的收尾快照）**
```
id=8  => CHK-20260929-001 | 状态=pending_review | 建单人=赵六 | 项数=1764
   → 里面 【测试】火花塞 A型：账=90 实=0 差=-90      ← 有人在整仓单里把火花塞填成了 0 个
id=10 => CHK-20260929-002 | 状态=pending          | 建单人=赵六 | 项数=1764
id=11 => CHK-20260929-003 | 状态=completed        | 建单人=赵六 | 项数=2
id=12 => CHK-20260929-004 | 状态=pending_review   | 建单人=赵六 | 项数=1764
id=13 => CHK-20260929-005 | 状态=completed        | 建单人=赵六 | 项数=1
id=14 => CHK-20260929-006 | 状态=completed        | 建单人=赵六 | 项数=1
```

**16）实测：负数实盘会不会真把库存写成负数？（我请王总审核，之后我立刻还原了）**
```

③ POST check review {id:13, approve:true}（王总）→ {"code":0,"message":"审核完成，已调整 1 项差异库存"}

⑤ 还原：再建单 CHK-20260929-006 实盘填回 162 → 王总审核 → current_stock: 162 ✔（已恢复）
```

## 我这个岗位愿不愿意继续用？为什么？

**不敢用。要是让我天天拿它签字，我不签。**

先说我认的东西，这些都是好的：

1. **提交出库/入库的那一刻库存就动了，而且并发出入库 8 连发一分不差**（88→80、80→88）。这个底子，比我用过的纸单子和 Excel 强。
2. **确认出库单不改库存**——单据和库存两个动作分开，这思路是对的。
3. **盘点提交不直接改账，必须有人审**——这是我最看重的一条红线，系统守住了。
4. **库存流水能一路还原出当前库存**，45 条一笔一笔严丝合缝，能追到哪张单、哪个人、什么时间。这一点真不错。
5. **权限的大部分门是关着的**：趋势、操作员统计、物料排行、用户管理、删除物料，我挨个试全被拦了。

但作为一个要在上面签字的人，我不能用，就因为下面这几条：

- **我最怕的那种事，出现了。** 盘点单告诉我火花塞"账 93 → 实 88、差异 -5"，流水告诉我实际只调了 2.5 个（90.5 → 88）。**单据说丢了 5 个，流水说丢了 2.5 个。** 一旦真丢货、老板拿单据找我，我按哪个数赔？我 8 年仓管，最恨的就是"账上两个数"。
- **我建的盘点单，建完就消失了。** 列表里永远是空的，我自己都看不见，取消也取消不掉（403）。盘点这个活**我做不完也收不了尾**，只能一直求管理员。一个让我干不完的活，就是废活。
- **一张想把火花塞清成 0 的整仓盘点单，正躺在待审队列里，我连它存在都不知道。** 1764 项、覆盖整个配件仓、填着别人物料的数。它只要被审一次，我仓库的账就没了。这不是"有点风险"，这是**头顶上有把刀**。
- **库存能被盘成负数**（我亲手把它变成了 -3 个空气滤芯）。负数库存是仓库里根本不存在的东西，系统连一句提醒都没有。**这种账我签了字就是我的责任。**
- **我能扣别人仓库的库存。** 我一个配件仓仓管，往成品仓的单子上填一笔就成功了，成品仓少了 1 个。今天是我测试手滑，明天就是真丢货查不到人。**我要的是"我碰不到不属于我的货"**，系统不给我这个保证。
- **库存里出现了 89.5 个火花塞。** 我在货架上永远数不出半个火花塞。只要有小数，我每次盘点都差一点、永远对不平。
- 再加上：确认前我看不到余量（只好跑去货架数）、驳回按钮是死的、确认按钮点了 8 次都说"成功"、首页"本仓物料"的数字跟我数的差 151 个。

**关于"这个系统里的库存数字，我敢不敢签字"：**

> **账实能对上（我数多少，回写多少，这点诚实）；但"差异"和"为什么差"这两个东西，系统给不出对的数。**
> 我签字靠的就是这两个东西。所以：**当前版本，不敢签字。**
> 什么时候我敢签？三件事做到就行：
> ① **盘点范围能由我指定**（不是一开就是整仓 1764 项），并且**我能在列表里看见我自己的单**；
> ② **盘点单上的"差异"必须等于实际库存调整量**，对不上就要报错拦下来，而不是悄悄记个好看的数；
> ③ **负数进不去、小数进不去、不是我这个仓的货我碰不到**。
> 这三条做到了，这个系统比我现在的纸单子强得多，我很愿意用。
