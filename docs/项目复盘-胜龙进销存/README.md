## 一句话结论

**这个项目真正的转折点不是写完功能，而是承认「测试通过 ≠ 可以上线」。**

前 16 天在堆功能、修单点 bug；10-16 那天用户说「测了这么多遍还是有 bug，我真的怕了你」，
才逼出正确的诊断：**不是测得少，是测的对象错了** —— 一直在测「功能对不对」，
没测「代码 / 数据库 / 部署这三者是否一致」。改完之后补的是一套**发现问题的机制**，
不是又一轮手工测试。

## 一、八条判断错误（最值钱的部分）

每一条都是真实发生、有代价的。按「错在哪 → 代价 → 现在的做法」写。

### 1. 把「本地全绿」当成了「可以上线」

- **错在哪**：本地库结构最新、账号齐备、openid 齐全、数据干净 —— 所以单测、接口冒烟、手工点全都过。
- **代价**：三个真缺陷全部溜到生产才被发现。其中「采购录价」是**100% 必现 500**（`Unknown column 'channel_remark'`）。
- **根因**：代码要写一列，而**库和 `schema.sql` 两边都没有这列**。
  原来的漂移检测是「库 ⇄ schema.sql」，两边同缺就报「无漂移」—— **盲区正好在这里**。
- **现在的做法**：加一道「代码实写的表.列 ⇄ 库」的审计（`check-code-schema.js`），
  不问 schema.sql 怎么说，直接看代码到底用了哪些列。

> 推广：**任何「A 和 B 一致」的检查，都要问一句「如果 A 和 B 一起错了呢」。**

### 2. 把「自己造的数据」当成了「生产事实」

- **错在哪**：看到盘点单 `stock_checks.id=116` 的 `operator_openid='zhaoliu'`（一个无 openid 的仓管），
  据此断定「盘点人员下拉过滤 openid 是缺陷」。
- **代价**：写进文档、写进记忆、还准备改代码。
- **反转**：那张盘点单是**我当天 18:16 做全量盘查时自己建的测试单**。
  复查生产库后真相是：`文彬`（id=41，有 openid）是唯一真实人员，
  `张三/李娜/赵六/王总` 是 2026-09-29 **同一秒批量建的演示账号**。
  → 过滤是**正确的刻意设计**，代码没错。
- **现在的做法**：拿任何数据当证据前，先查它的 `created_at` 和 `remark`，
  **确认它不是自己刚造的**。「自己造的证据不算证据」。

### 3. 把「扫描器写的判据」当成了「业务真相」

- **错在哪**：隐患扫描器首版把「入库单状态 `pending` 却有库存流水」报成异常。
- **代价**：差点去"修"一个不存在的问题。
- **真相**：本系统**入库 = 提交即入账**（`submit` 就加库存），所以 pending 有流水完全正常；
  而出库相反，**确认收货才扣库存**。
- **现在的做法**：写判据前先读代码，把**真实不变式**确认下来；
  扫描器 0 命中时，用一组**已知非零的真实数字**做反向对照，证明它真的在数
  （本次用 1907 物料 / 8 流水 / 8 账号验证）。

> 推广：**扫描器本身是代码，也会错，而且它错了你更信它**（因为它看起来客观）。

### 4. 把「文档里的数字」当成了「现在的数字」

- **错在哪**：录屏脚本写「水鞋库存 10」，交付前没复核。实际只剩 **5**（盘查时出库演示扣过）。
- **代价**：如果照着填 6 以上，录制过程中会当场弹「库存不足」，**录到一半卡住**。
- **现在的做法**：给用户「照着做」的材料前，**所有会变的数字都对着生产库重核一次**，
  并在文档里标上「核实时间 + 真值」。

### 5. 以为「配置备份放哪都行」

- **错在哪**：改 nginx 前把配置备份成 `sl.ekkosys.cn.bak-1016-2108`，**留在了 `sites-enabled/` 目录里**。
- **代价**：`nginx.conf` 用 `include /etc/nginx/sites-enabled/*` **通配加载** ——
  备份文件被当成**第二份生效配置**，`server_name` 冲突，改动看起来「没生效」。
- **现在的做法**：备份放 `/etc/nginx/backups-ekko/`（include 范围外），
  并把这条写成运维扫描器 `scan-ops.sh` 的检查项 5b。

> 推广：**「备份」和「生效配置」在同一个被通配加载的目录里，备份就等于第二份配置。**

### 6. 把「本机请求失败」当成了「服务端有问题」

- **错在哪**：冒烟时出现 1 次 `ECONNRESET`、复现时 8 次里 1 次 10 秒超时；
  又曾探测到「3000 端口返回 502」以为端口暴露了。
- **代价**：差点去修一个不存在的问题，还可能误判「端口没封」而做多余的加固。
- **真相**：本机有 `http_proxy=127.0.0.1:60192`，curl 打任何端口都会命中它并返回
  **502 + Windows 错误码**；超时也是本机链路。
  **从服务器本机复测 30 次：全部 0.00–0.09 秒、零超时。**
- **现在的做法**：判断「是不是生产的问题」前，先做**对照实验** ——
  从服务器内部再发一遍。看到「Windows 错误码」就说明是本地代理。

> 推广：**凡是"偶发失败"，先排除自己的观测工具，再怀疑被测对象。**

### 7. 把「顺序」当成了可以随便排的事

- **错在哪**：把「企微加员工」排在「小程序上架」之前，还写成"最该先做"。
- **用户纠正**：小程序都还没上架，把人拉进通讯录，人家打不开会觉得**系统有问题**。
- **现在的做法**：企微加员工挪到**上架、员工第一次真正用上之后**。
  顺带查实：**不加企微不影响任何功能**（推送前按 `wecom_userid<>''` 查人，
  一个都没绑就直接 return，连 API 都不调；且是 `setImmediate` fire-and-forget）。

> 推广：**技术上的"可以先做"≠ 业务上的"应该先做"。** 任何涉及第三方的动作，
> 先想「对方此刻看到的是什么」。

### 8. 以为「对话里说过就行了」

- **错在哪**：口播稿、填表清单都只发在对话里。
- **代价**：几次网络中断（`Network error occurred`）+ 一次上下文压缩之后，
  用户反馈「录屏脚本那段没有了」，只能重发。
- **现在的做法**：**凡是用户要"照着做"的东西，必须落成独立文件**
  （本次产出 `docs/录屏台本-一页纸.html`，可打印、可手机直看）。

## 二、被验证有效的六个方法

### 1. 对照实验（最常用）

判断一个问题「是不是真的」，先找一个**参照物**：

| 场景 | 参照物 |
|---|---|
| 怀疑服务端 500 | 从服务器本机再发一次 |
| 某个检查 0 命中 | 用已知非零的真实数字验证它真的在数 |
| 48 个文件全不一致 | 先怀疑行尾（CRLF/LF）差异 |

### 2. 判据必须先读懂不变式

写任何「检查」之前，先回答：**这个系统在这件事上的真实规则是什么**。
本项目的两条反直觉规则差点让扫描器写错：

- **入库 = 提交即入账**（submit 就加库存）
- **出库 = 确认收货才扣**（`stock_deducted=1` 在 receive，驳回作废据此回补）

两者**方向相反**，写判据时搞反过一次。

### 3. 豁免必须可见，不许静默消音

lint 一度把「刻意豁免的违规」只收进内部变量、**输出里不显示** —— 等于无声消音，
而这正是让缺陷藏起来的标准手法。改成**连理由一起打印**：

```
· user.js:519  豁免：盘点执行人须能登录小程序执行盘点，无 openid 账号登不进
```

### 4. 闸门要打印「证据」而不是「结论」

部署一致性检查最初只播报「本地有而生产没有：3 条」，而实际上两边 49 个文件一个不缺
（内容不同的文件两侧都会出现）—— **闸门自己说错话，等于把人训练成不看它**。
改成按文件名集合求差 + **打印真实 diff 前 12 行**，一眼能看出
「是实质改动还是只改了注释」，这直接决定要不要重启服务。

### 5. 留痕，不留「应该是」

- 重启只证明 `is-active` **不够**（旧进程活着也是 active）→ 必留 **PID 前后对照 + `ExecMainStartTimestamp`**
- 部署前先 `node --check`，避免带着坏文件重启
- 回滚点、临时令牌、临时目录**用后即删**并留记录

### 6. 三个始终要问的问题

1. **这个证据是我自己造的吗？**（是 → 不算）
2. **这个数字现在还是这个数吗？**（不确定 → 查）
3. **如果 A 和 B 一起错了呢？**（一致性检查的盲区）

## 三、这个系统特有的坑（给接手的人）

技术栈：小程序（uni-app）+ 后台（Vue3/Element Plus）+ Node 后端，统一分发式接口
`POST /api/<模块>` + `{action, data}`。

| 坑 | 说明 |
|---|---|
| **入出库扣账时机相反** | 入库提交即入账；出库确认收货才扣。写判据别搞反 |
| **后台账号没有 openid** | 身份口径必须 `COALESCE(openid, username)`。曾导致「消息已读必然 401」「采购指派下拉永远空」 |
| **小程序登录按 openid 找人** | 查不到就新建 `pending` 账号 → **后台手工建的账号永远认领不了原身份**。正规入场路径是「员工先扫码进来建号，后台再给角色」 |
| **分类口径是 `sub_category`** | `category` 是仓库级大类，一个仓只有一个值，用它筛等于没筛 |
| **生产目录不是 git 仓库** | 部署靠手动传文件，**漏传没有任何机制能发现**。只能靠逐文件哈希对撞 |
| **扫码即建档** | 任何人扫到小程序码都会得到一个 `pending` 零角色账号 → 必须显式拦截，否则能读到库存、成本价、供应商电话 |
| **生产 `/opt/shenglong` 与本地是两套** | 生产 6 个账号里 5 个无 openid；本地则齐全 → 行为差异的根源 |

## 五、如果重来一次

按投入产出排序，这五件事应该提前做：

1. **第一天就建闸门**，而不是等出事。
   成本大概半天，能省掉后面三天的返工和一次「用户对你失去信心」。
2. **生产用 git 部署**（哪怕只是个裸仓库 + `post-receive` hook）。
   手动传文件这种事，**漏传是必然而不是意外**。
3. **演示/测试数据从第一天就带统一标记**（如 `remark` 含 `【测试-可删】`），
   并提供一个一键清理脚本。本次盘查造的数据散在入库单、出库单、盘点单、采购任务、
   物料、账号六处，只能一条条辨认。
4. **平台后台操作一律「先截图再下结论」**。本次连踩三次同源的坑
   （服务内容下拉、前置审批项、人脸核身背景），都是凭文档推演界面导致的。
5. **文档里凡是会变的数字，都标「核实时间」**，交付前重核。
