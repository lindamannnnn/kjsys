## 二、我报的问题

### [P2] 首页「仓库列表」没有按可管仓库收敛，领料员看得见「成品仓」

- **我做了什么**（原始请求）：
  ```json
  POST /api/warehouse  { "action": "list", "data": {} }   // token: dev_out（可管仓库 [1]）
  ```
- **系统回了什么**（原始响应，贴关键字段）：
  ```json
  {"code":0,"data":{"list":[
    {"code":"peijian","name":"配件仓","material_count":1770,"total_stock":99425,...,"_id":1},
    {"code":"chengpin","name":"成品仓","material_count":149,"total_stock":3933,...,"_id":2}
  ]},"message":"操作成功"}
  ```
  对照：同一个 token 查 `stats.stockList{warehouse_id:2}` 返回 **空列表**（total 0），提单到仓库 2 被 **403** 拦下。
- **我认为哪里不对 / 应该是什么样**：手册 §2.5 明确「所有查询按可管仓库自动收敛」。`dev_out` 只能管 [1]，首页却把「成品仓」也列出来，还带着 149 个物料/3933 库存的数字。我（一个不太会用电脑的领料员）会以为能去成品仓领料，点进去提单却报「无权限」——白跑一趟的电子版。**建议 `warehouse.list` 也按可管仓库过滤**，或至少对无权限仓标注「仅查看/不可操作」。
- **有没有证据**：有证据（上方原始请求 + 响应，及 403/空列表两条对照）。

### [P2] 消息中心有一条通知指向「不存在的单据」，且与真实单据共用同一单号

- **我做了什么**（原始请求）：
  ```json
  POST /api/message { "action": "list", "data": {} }         // dev_out
  POST /api/outbound { "action": "detail", "data": {"id":598} }   // dev_out，随后再用 dev_sk 复核
  ```
- **系统回了什么**（原始响应，贴关键字段）：
  ```json
  // message.list 中两条：
  {"type":"outbound_picked","content":"OUT-20261003-018 已完成拣货（共 1 项）…","ref_id":598,"ref_no":"OUT-20261003-018","is_read":0,"_id":107,"created_at":"2026-10-03T11:10:24.000Z"}
  {"type":"outbound_picked","content":"OUT-20261003-018 已完成拣货（共 2 项）…","ref_id":608,"ref_no":"OUT-20261003-018","is_read":1,"_id":143,"created_at":"2026-10-03T11:44:01.000Z"}
  // detail(598)，领料员与仓管两个 token 都是：
  {"code":404,"data":null,"message":"单据不存在"}
  // 而 detail(608) 正常返回 OUT-20261003-018
  ```
- **我认为哪里不对 / 应该是什么样**：两条通知挂着同一个单号 `OUT-20261003-018`，但 `ref_id` 一个 608（真单、已完成）、一个 598（不存在）。领料员点那条通知想跳详情，会吃一个「单据不存在」。合理的做法：单据被删除/作废时同步清掉或置灰对应通知；单号也不应被两条不同单据复用。
- **有没有证据**：证据充分（消息原文 + 两个 token 的 404 + 608 的 200 对照）。**附一个推测**：598 与 608 曾拿到同一个单号 `018`（内容里「共 1 项」vs「共 2 项」），疑似 598 被删后单号被重新发给了 608 —— 这一点我拿不到 598 的历史记录，只能标「推测」。

### [P2] 「我的单」里存在「待确认」但库存已扣减的自相矛盾单据（疑历史遗留）

- **我做了什么**（原始请求）：
  ```json
  POST /api/outbound { "action": "list", "data": {"page":1,"page_size":20} }   // dev_out
  ```
- **系统回了什么**（原始响应，贴关键字段）：
  ```json
  {"order_no":"OUT-20261001-008","status":"pending","status_text":"待确认","stock_deducted":1,"_id":580}
  {"order_no":"OUT-20261001-004","status":"pending","status_text":"待确认","stock_deducted":1,"_id":576}
  ```
  （对照：我刚提的 609 是 `status:"pending","stock_deducted":0`）
- **我认为哪里不对 / 应该是什么样**：按手册 §2.1，库存在 `receive` 那一刻才扣，「待确认」阶段 `stock_deducted` 应为 0。这两张单显示「待确认」却已扣库存，状态与库存标记互相矛盾；若后续被正常确认→拣货→收货，存在**二次扣减**风险。合理做法：要么状态推进，要么 `stock_deducted` 归零。
- **有没有证据**：有证据（`outbound.list` 原始响应）。**但标「推测」**：这两张是 10-01 的 E2E 遗留单，疑似历史数据迁移造成，非本轮产生，建议由管理员核账。

## 三、系统做对的地方

1. **幂等真的生效**：同一 `client_request_id` 重复 `submit`，返回**同一** `_id:609 / OUT-20261003-019` + `duplicated:true`，没有重复建单，列表总数不变。（这是我最怕丢单的地方，系统做对了。）
2. **库存扣减只在收货那一刻、且数字精确**：608 收货后刹车片 15→13、空气滤芯 35→30；607 收货后火花塞 95→91、机油滤芯 39→37，`stock_deducted` 同步置 1，`receive_operator=dev_out`、`received_at` 齐全。
3. **跨仓操作被正确拒绝且文案清楚**：拿成品仓物料提单，`403「你没有「出库单」所在仓库的操作权限，请联系管理员分配」`——一句话说清原因，不是含糊报错。
4. **消息按 openid 隔离、已读联动正确**：`markRead{143}` 后 `unreadCount` 2→1，`only_unread:true` 只剩 107；首页/消息中心/待办三处未读数一致。
5. **首页待办主动聚合**：`outbound.myNotice` 把我该干的活（待收货）直接列出来，还带了 `item_count` 和操作人，我不必自己翻列表找。
6. **提交时给了「库存是否够」的预防信息**：`detail` 里每项带 `current_stock` + `stock_enough:true`，提单前能判断会不会白跑。
7. **数据权限在统计口径也生效**：`stats.stockList{warehouse_id:2}` 对领料员返回空，不泄露成品仓库存。
