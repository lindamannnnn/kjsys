## 三、P0 致命问题（1 条）

### [P0] 入库单"提交后撤销"，库存数量退回来了，**加权成本没退回来**

**现象**：提交一张入库单（比如 10 个 @100 元），再撤销它。库存数量正确退回，
但**加权平均成本原地不动** → 库存金额虚高，而且**任何角色都没有自助手段修回来**。

**三个岗位独立复现**（互不知情）：
- 采购员李娜：机油滤芯撤销后数量 111→101，成本停在 17.8715（应回 9.74），虚高 **821.28 元**
- 仓管员赵六：刹车片成本被从 90 抬到 105.71、又到 108.90，撤销后原地不动，虚增 **1133.96 元**
- 老板王总：轴承 F 最小复现（40@22 → 入库 10@60 → 撤销，数量回 40、成本停在 34.08，应回 22）

**本次测试的实测数据（清理前）**：

| 物料 | 初始成本 | 测试后成本 |
|---|---|---|
| 【测试】刹车片 C型 | **88** | **108.8993** |
| 【测试】机油滤芯 D型 | **9.9** | **17.7136** |

**独立验证结论（源码级根因，我已复核）**：

`server/src/services/stock.js:213` ——

```js
/** 入库撤销（若业务需要）：数量减少，成本不变 */
async function restoreForInboundCancel(conn, { material, quantity, orderNo, operator }) {
  const q = qty(quantity)
  return applyChange(conn, { material, delta: -q, changeType: 'inbound_cancel', ... })
}
```

而 `applyChange`（同文件 82-137 行）**只执行** `UPDATE materials SET current_stock = ?`，**完全不碰 `avg_cost`**。

对比入库时 `addForInbound`（172-211 行）：它会完整重算 `avg_cost = (原库存金额 + 本次入库金额) / 总数量`。

**两者不对称**：入库改了成本，撤销却不还原成本。代码注释写着"成本不变"，但这不是业务约定
（手册第四节列出的 12 条"本来就该这样"里没有这一条，界面上也没有任何提示）。

**为什么这是 P0**：
- 它让**库存金额**（`current_stock × avg_cost`）永久性失真，且没有任何流水记录可追溯
- 出库成本、库存总价值、对账单全部跟着错
- 用户**无法自救**（没有成本调整接口，改价只对未确认单有效）

**修复方向**（供参考）：撤销入库时按当时入库的单价反向冲减库存金额，
并写一条 `price_adjust` 类的成本修正流水；或在入库单上冗余记录"变动前的 avg_cost"，撤销时还原。

## 五、已排除的"假问题"（复核后判定不是缺陷）

### 1. 「已确认的单子，仓管一律作废不了」—— 这是设计，不是缺陷

赵六报为 P1。我读源码后判定**这是有意的权限收紧**：

```js
// outbound.js / inbound.js
if (order.status === 'confirmed' && !isManager) {
  return fail(403, '该单据已确认，仅管理员可作废')
}
```

`isManager = hasAnyRole(user, ['boss','admin'])` —— 已确认的单只有老板/管理员能作废。
提示语也是清楚的。赵六的诉求（"我自己确认错了想马上改"）是**合理的产品建议**，但不是代码缺陷。
**建议保留设计，可考虑给仓管加"申请作废"流程。**

### 2. 关于登录方式差异

本次测试用账号密码登录，真实环境用微信登录（有 `openid`）。
历史上这一差异曾导致"自己看不到自己的单据"的假问题，**本次未复现** ——
因为系统已统一为 `identityOf(user) = openid || username`，写入与读取走同一个函数（见 `middleware/auth.js:87`）。

## 六、系统做对的地方（整改时请勿误伤）

这部分同样重要 —— 否则修 P0 时容易把这些好设计一起改坏。

1. **库存只能走单据**：`material.upsert` 明确拒绝写 `current_stock` / `avg_cost`，
   提示"库存只能通过入库单或盘点调整变更，这样才能留下可追溯的流水与责任人"。实测拦住。
2. **不允许负库存**：出库时校验并给出**带量纲的清晰提示**（"当前库存 85 个，本次需减少 100 个"）。
3. **驳回必须填理由**：`outbound.reject` 不带 `reason` 直接拒绝，提示"提交人需要知道为什么被退回"。老板也绕不过。
4. **一张单不能混多个仓库**：会明确报错要求分开提交。
5. **幂等机制存在**（虽然被前端写法削弱）：带相同 `client_request_id` 重复提交只生效一次。
6. **盘点双人接力**：仓管/老板建单 → 仓管录入提交 → **只有老板能审核**，仓管审不了自己提交的。
   退回时库存完全不动。
7. **仓库隔离真实生效**：实测出库员/采购员搜成品仓物料返回 **0 条**；越权调用一律 403。
8. **数量对账完全可追溯**：6 条测试物料逐笔流水还原，与当前库存**差额全为 0**；
   谁提交、谁确认、哪张单、前后数量，条条能追到人。
9. **越权防护到位**：4 个岗位共尝试了几十次越权（改盘点审核、看趋势、管用户、改真实物料库存），**全部被拦**。
10. **盘点全盘守卫**：不选具体物料且物料过多时，要求二次确认，避免误建上千项的单子。

## 七、修复优先级（按"一次能修完 + 决定能不能用"排序）

### 第一批：发布前必改（决定系统能不能管真资产）

1. **[P0] 入库撤销回退成本** —— 唯一的金额级缺陷。修完 4 个岗位中有 3 个愿意签字。
2. **[P1] 前端提交加锁** —— 提交期间禁用按钮 + `showLoading` 加 `mask:true`；
   同时把 `client_request_id` 改为**每次"打开提交页"生成一次**、重试时复用，幂等才真正生效。
3. **[P1] 供应商必填** —— 入库单不给空供应商，`supplier_id` 需校验存在。
4. ✅ **[P1] 后台白屏** —— **本次已修复并部署验证**。

### 第二批：影响信任，尽快修

5. **[P1] 预警口径统一** —— 看板与明细页统一用 `<=`，并统一是否隐藏 idle 物料。
   （要么看板也过滤 idle，要么明细页默认显示全部并保留 `includeIdle` 开关）
6. **[P1] 单价加合理上限**（比如 100 万）—— 防手滑写多几个零。
7. **[P1] 采购月度汇总** —— 采购员需要"这个月买了多少、花了多少钱"，目前给不全。

### 第三批：体验优化（13 条 P2）

合并去重后包括：出库单缺「领料人」栏、仓库切换条列出无权仓库且无提示、出库类型接口不校验、
搜索提示未说明可按编号搜、重复确认提示夹英文日期、流水页撤销按钮形同摆设、
停用物料后未结单据撤不了、流水列表看不到确认人、趋势"7 天"给 8 个点、
人员统计是历史开发账号、单价 0 能入库、关键词搜不到备注、加权成本 0.0001 级尾差。

### 关于盘点审核覆盖问题的建议（原 P1 降级为 P2）

系统已经检测到"盘期间发生过出入库"并写在流水备注里，但**审核界面上没有突出提示**。
建议审核时如果检测到账面已变动，在返回结果里明确告诉老板："本单盘点期间该物料发生过 N 次出入库，
审核将把库存直接设为实盘数 X，期间的出入库记录会被覆盖" —— 让老板知情后再决定。
