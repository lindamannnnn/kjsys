## 二、我报的问题

### [P1] 同一物料拆成多行即可绕过提交时的库存校验，产生无法收货也撤不掉的「僵尸单」

- **我做了什么（原始请求）**：
  ```json
  POST /api/outbound
  {"action":"submit","data":{
    "warehouse_id":1,"type":"lingyong","remark":"[V3-R2] Y1拆行超卖-全流程",
    "items":[
      {"material_id":2100,"material_name":"【测试】火花塞 A型","quantity":60,"warehouse_id":1},
      {"material_id":2100,"material_name":"【测试】火花塞 A型","quantity":60,"warehouse_id":1}
    ]}}
  ```
  （单行 60 ≤ 库存 91，但两行合计 120 > 91）
- **系统回了什么（原始响应，贴关键字段）**：
  ```json
  {"code":0,"message":"领料单已提交，等待仓管确认拣货","data":{"_id":618,"order_no":"OUT-20261003-028"}}
  ```
  后续 `confirm` → `{"code":0,...}`、`pickDone` → `{"code":0,...}` 全部放行，单据进入 `receiving`。
  真正到 `receive` 才被挡（负库存保护 + 事务回滚）：
  ```json
  {"code":400,"message":"库存不足：【测试】火花塞 A型（规格 TEST-SPK-A） 当前库存 31 个，本次需减少 60 个。请先入库补货，或联系仓管核对库存","data":null}
  ```
  此时单据卡在 `receiving`：**领料员本人撤不了**（新规则：receiving 阶段只能仓管/老板/管理员撤），
  最后是我用仓管身份 `cancel` 才清掉的。
- **我认为哪里不对 / 应该是什么样**：
  `outbound.js:35-49` 的 `assertStockEnough` 是**逐行** `stock < need` 判断，**没有对同一 `material_id` 汇总**。
  提交时应对 `items` 按物料归并求和后再比库存，把这张单在**提交那一刻**就拦下；
  否则用户以为提交成功、仓管也确认拣货了，货到手上却收不了，单据既发不出去也撤不掉，白折腾一趟。
- **有没有证据**：**有**（`.tmp-local-audit/out-r2/raw/` 中 `*-outbound-submit-out.json`、`*-outbound-receive-out.json`；库存最终回到 91，事务回滚正确）

### [P2] 重复确认收货的提示里塞了一段 JavaScript 原生 Date，中文界面里很突兀

- **我做了什么（原始请求）**：对已完成单再收一次货
  ```json
  POST /api/outbound
  {"action":"receive","data":{"id":611}}
  ```
- **系统回了什么（原始响应）**：
  ```json
  {"code":0,"message":"该单据已于 Sat Oct 03 2026 19:54:14 GMT+0800 (中国标准时间) 确认收货，无需重复操作",
   "data":{"duplicated":true,"received_at":"2026-10-03T11:54:14.000Z","stock_deducted":true}}
  ```
- **我认为哪里不对 / 应该是什么样**：
  幂等本身是对的（好事），但提示文案是 JS `Date.toString()` 的默认格式——英文星期 + 时区英文串，
  和全站其它地方的 `2026-10-03 19:54` 风格不一致。建议统一格式化成 `2026-10-03 19:54`。
- **有没有证据**：有（原始响应如上）

### [P2] 收货被库存挡下时，报错里的「当前库存」是事务中间值，会把人看懵

- **我做了什么（原始请求）**：同上 Y1 的单 `receive`
- **系统回了什么（原始响应）**：
  ```json
  {"code":400,"message":"库存不足：… 当前库存 31 个，本次需减少 60 个。…"}
  ```
  而同一时刻该物料真实库存是 **91**（`material.detail` 复查 = 91）。
  「31」是事务里第一行先扣掉 60 之后的中间值，事务已整体回滚，但提示没跟着还原。
- **我认为哪里不对 / 应该是什么样**：
  仓管/领料员看到「当前库存 31」会以为库存真只剩 31，可能去做无关的补货动作。
  提示应使用事务开始前的真实库存（91），或干脆对同一物料汇总后只报一次。
- **有没有证据**：有（上条响应 + `material.detail` 复查 91）

### [P2]（口径）手册 §2.5 说「查询按可管仓库收敛」，但领料员实际只能看自己提交的单

- **我做了什么（原始请求）**：
  ```json
  POST /api/outbound  {"action":"detail","data":{"id":619}}   // 619 由仓管在配件仓(1)提交
  ```
- **系统回了什么（原始响应）**：
  ```json
  {"code":403,"message":"只能查看自己提交的单据","data":null}
  ```
  （619 也不出现在领料员的 `outbound.list` 中）
- **我认为哪里不对 / 应该是什么样**：
  这个限制本身**更严、更安全**，对领料员岗位（「我的单」）也合理，我不认为是漏洞。
  但手册 §2.5「所有查询按可管仓库自动收敛，dev_out 只管 [1]」的措辞会让人以为领料员能看到配件仓**全部**单据。
  建议手册改成「领料员只可见自己提交的单据（按提交人收敛）」，避免后续测试误判。
- **有没有证据**：有（原始响应如上）

## 三、系统做对的地方

1. **数量非法全拦得住**：超库存 / 0 / 负数 / 小数 / 非数字，五种都为提交前的 400，文案还带单位与规格，车间工人看得懂（A1–A4、Y2）。
2. **越权开单拦得住**：领料员提「报废」→ 403；碰成品仓物料 → 403；「仓库与物料对不上」→ 400。
   而且我专门试了「不传 warehouse_id」「把物料仓改成 1 伪装」等绕过姿势，**都没绕过去**（B5/B6/B6b、X1/X2/X3）。
3. **越权操作拦得住**：领料员调 `confirm`/`pickDone` → 403「无操作权限」；对别人提交的单 `receive` → 403「只有该单的领料人或仓管可以确认收货」（Y3/Y4、C7）。
4. **「提交不动库存、收货才扣库存」这条语义是真的**：撤待拣货单 610 前后库存纹丝不动（91/37）；
   收货 611 的瞬间 2102:13→11、2104:30→25。含负库存保护的**收货事务回滚也是对的**（Y1 收货失败后库存仍是 91）。
5. **撤销规则（本轮新）完全符合手册 §2.1**：新建单 10 分钟内可自撤（C8）、待拣货可自撤（C9）、
   待收货不可自撤（C10）、已完成不可撤（C11），提示语各不相同且准确。
6. **幂等靠谱**：同 `client_request_id` 提交两次只建一张（返回原单 + `duplicated:true`）；重复收货也返回 `duplicated:true`，不会重复扣库存（C12/C13）。
