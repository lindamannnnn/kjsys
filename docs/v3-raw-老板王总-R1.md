## 二、我报的问题

### [P1] 盘点审核：传 `approve:"yes"` / `2` 不会被拦下，而是被**悄悄当成「退回」执行**

- 我做了什么（原始请求）：
  ```json
  POST /api/check  {"action":"review","data":{"id":169,"approve":"yes","remark":"[V3-R1] 复现：意图通过却传了yes"}}
  ```
- 系统回了什么（原始响应）：
  ```json
  {"code":0,"data":{"approved":false,"adjusted":0},"message":"已退回，库存未做任何调整，请重新盘点后再提交"}
  ```
  `approve:2` 同样返回 `{"code":0,...,"approved":false}`「已退回」。用作对照，「不传」是被正确拦下的：
  ```json
  POST /api/check  {"action":"review","data":{"id":168}}
  → {"code":400,"data":null,"message":"请明确选择「通过」或「退回」"}
  ```
- 我认为哪里不对 / 应该是什么样：
  手册第 2.4 节白纸黑字写着：「**不传 / 传 `"yes"` / 传 2 都按「没表态」拦下**」。服务端 `check.js:435-436` 的注释也写着「传了乱七八糟的值（"yes" / 2 / 对象）一律当作「没表态」拦下 —— 盘盈盘亏是要动物流账的，绝不能因为参数写错就默认放过」。
  但实际代码（`check.js:437`）**只拦 `undefined / null / ''`**，第 440 行 `approve = rawApprove === true || 'true' || 1 || '1'`，凡是"传了但值不等于真"的，全部落进第 460 行 `if (!approve)` 的**退回分支**。
  后果：我明明想「通过」，只要前端/对接方把布尔值写成了字符串 `"yes"`（或传了 2），系统不但不报错，还会**把我的审批动作静默变成退回**，单据被打回重盘。老板的审批结果被悄悄反转，这是很容易踩的坑。
  正确行为应当是：`"yes"` / `2` / 对象一律按「没表态」报错拦下（只有 `true / 'true' / 1 / '1'` 才算通过）。
- 有没有证据：**有证据**（原始请求 + 原始响应 + 代码定位 `check.js:437/440/460`）。同一现象在 164、169 两张单上各复现一次。

## 三、系统做对的地方

1. **看板计数与明细完全对得上**：`overview.warning_count=30`，而 `stats.warning` 明细 `total=30`；`overview.zero_count=11`，明细 `out_of_stock=11`。分仓也闭合：配件仓 28 + 成品仓 2 = 30；`total_stock` 99425+3933=103358，`material_count` 1770+149=1919。老板最在意的"数字一致"这条，站得住。
2. **库存流水账实相符、链条闭合**：火花塞 A型 11 笔流水 `+100-5-5+5-10-1+1-1+1-1+1` 累加 = 85 = `net_quantity` = 当前库存；每笔 `before_stock→after_stock` 首尾相接。齿轮 G型 链条 `0→24→34→37` 同样闭环。这是"账实相符"的硬证据。
3. **盘点审核门禁保住了底线（没出现 P0）**：`check.review` 不传 `approve` 时被明确拦下（`code=400「请明确选择「通过」或「退回」」`），**没有"默认通过"**。盘盈盘亏会动物流账，这一步没放水，是这次最重要的正确点。
4. **盘点通过后库存按实盘数调整且可追溯**：168 通过后 `adjusted:1`，齿轮 G型 34→37，`stockFlow` 里出现一笔 `盘点差异调整 +3`，与单据差异一字不差，流水可回查。
5. **单据流水状态是中文文案**：`orderFlow` 每单都带 `status_text`（待确认/待拣货/待收货/已完成/已作废/已驳回），没有把英文旧状态名（如 `receiving`）直接甩给用户看。
6. **预警明细讲道理**：30 条预警的 `current_stock` 都 ≤ `warning_stock`，最低阈值是 5，**没有"阈值为 0 却报预警"**；7 个 `【测试】` 物料库存都在阈值之上，一条都没被误报。
7. **角色/仓库权限正确**：`user.list` 里仓管 `dev_sk` 的 `warehouse_ids=[1,2]`（配件仓+成品仓）确实管两个仓，领料员只 [1]，与手册一致。
8. **站内消息按 openid 真实投递**：换 token 旁证可见仓管收到 51 条、领料员 3 条，不同人的消息互不串——按人隔离是对的。
