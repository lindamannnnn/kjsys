## 一、现状盘点（已核实的代码事实）

### 1.1 角色

| 代码 | 当前中文名 | 现有职责 | 本次变更 |
|---|---|---|---|
| `out` | 车间员工 / 出库员 | 提交出库单（领料） | **改名「领料员」** |
| `in` | 仓库管理员 | 提交入库单 | **取消，并入 `storekeeper`** |
| `storekeeper` | 仓管员 | 确认/驳回单据、盘点 | **职责扩张**：确认 + 拣货 + 入库 + 发采购任务 |
| `purchase` | 采购员 | 提交采购入库单 | **职责收窄**：只管买 |
| `boss` | 老板 | 看板、预警、全部单据 | 增加两个仓总值 |
| `admin` | 管理员 | 全权 | — |

- `users.roles` 是 **JSON 数组**（不是 ENUM），角色合并只需数据迁移 + 代码判定调整，**无需改表结构**
- 角色中文名映射位置：`miniprogram/src/pages/index/index.vue`（约 224 行）、`pages/my/profile.vue`（约 184 行）
- 测试身份定义在 `miniprogram/src/utils/cloud.js`（`DEV_IDENTITIES`）

### 1.2 仓库

只有两个：**配件仓**（`peijian`）、**成品仓**（`chengpin`）。

### 1.3 物料档案

`materials` 表已有字段：名称、**规格 `spec`**、**大类 `category`**、**细类 `sub_category`**、物料编号、单位、当前库存、预警库存、**移动加权平均成本 `avg_cost`**。

- 后端 `material` 模块已提供 `upsert`（新增/修改）与 `categories`（取大类列表）
- `upsert` 权限：`boss / admin / storekeeper`
- ⚠️ **小程序端目前没有任何「新增物料」入口**（全项目搜不到 `callCloud('material', 'upsert')`），物料只能靠后台或导入脚本维护

### 1.4 三条单据流的现状

| 单据 | 状态机 | 库存变动时机 |
|---|---|---|
| 出库单 | 待确认 → 已确认 / 已驳回 / 已作废 | **提交时就扣库存** |
| 入库单 | 待确认 → 已确认 / 已作废 | **提交时就加库存**（并算加权成本） |

- 提交权限：出库 `out/purchase/storekeeper/boss/admin`；入库 `in/purchase/storekeeper/boss/admin`
- 确认权限：两者都是 `storekeeper/boss/admin`
- 现有确认页文案明确写着：「库存在提交时就已经变动过了，确认只是把单据状态变成生效」
- `outbound_orders.status` 是 **真 ENUM**（`pending,confirmed,cancelled,rejected`）→ 加状态需 `ALTER TABLE`

### 1.5 已有的好基础（可直接复用）

- **领料页已经是「购物车清单」模式**：`pages/out/submit.vue`（875 行）支持搜索、加入清单、多项数量调整、库存不足提示、一次性提交多项 —— 需求里的「购物车式清单」**已经存在**
- **老板要的仓库总值后端已经算好了**：`stats.warehouseSummary` 返回每个仓库的 `total_value = SUM(当前库存 × 加权成本)`，只是老板首页没展示

### 1.6 缺口

- ❌ 没有**采购任务 / 采购单**体系
- ❌ 没有**通知 / 消息中心**（所谓"通知"目前只有「被驳回的单据」查询）
- ❌ 没有**拣货 / 到场收货**环节
- ❌ 小程序端没有**新增物料**入口

## 二、目标流程

### 2.1 领料线（领料员 ↔ 仓管员）

**角色改名**：`out` 由「车间员工 / 出库员」→ **领料员**
**执行人**：确认、拣货、发货全部由**仓管员本人**操作（不新增「库工 / 发货员」角色）

```
领料员：加清单（可多项）→ 提交
   ↓  通知仓管员（消息中心）
① 待确认 ── 仓管员确认 ──→ ② 待拣货
   ↓  仓管员按单备货，点「拣货完成」
   ↓  通知领料员（消息中心）
③ 待收货 ── 领料员到场核对明细，点「确认收货」──→ ④ 已完成
                                        ↓
                                   ★ 此刻才扣减库存
```

**核心变化**：

| 项 | 现状 | 目标 |
|---|---|---|
| 状态机 | 待确认 → 已确认 | 待确认 → **待拣货** → **待收货** → 已完成 |
| 扣库存时机 | 提交时 | **领料员确认收货时**（拣货阶段不动库存） |
| 通知 | 无 | 提交 → 通知仓管员；拣货完成 → 通知领料员 |
| 新增动作 | — | 仓管：拣货完成；领料员：确认收货 |

### 2.2 采购线（仓管员 → 采购员 → 仓管员）

**职责重定义**：采购员**只负责买**，不再自己入库；入库由仓管员做。

```
仓管员：创建采购任务（选物料、填数量、可指定采购员）
   ↓
① 待领取 ── 采购员点「领取」──→ ② 已领取（生成采购单号）
   ↓  采购员去下单
③ 采购录入：单价 · 购买方式 · 淘宝单号 · 上传单据
   ↓  提交 → 通知仓管员
④ 待收料（采购员把货送到仓库）
   ↓  仓管员核对实物
⑤ 已完成（仓管员清点入库：加库存 + 算加权成本）
```

**分配方式**：仓管发任务时**可选指定**某个采购员；不指定则对全体采购员开放、先到先得（领取即锁定）。

**购买方式枚举**：`淘宝 / 京东 / 线下 / 其他`

**需要新增的采购任务字段（初拟）**：单号、物料、数量、状态、创建人（仓管）、指定人（可空）、领取人（采购员）、**实际单价（采购员填）**、购买方式、淘宝单号、单据附件、各节点时间。

### 2.3 入库线（仓管员）

- 入库提交权限**收敛到仓管员**（原来 `in` 和 `purchase` 都能提交）
- 新增功能「**新增入库项目**」：选**大类** → **填规格** 或 **从已有规格里选** → 加入入库单
  - 本质是补齐小程序端缺失的「新建物料档案」入口
  - 大类数据源已有（`material.categories`）；规格可选可填，避免每次手打

### 2.4 老板看板

在现有 KPI（今日出/入库单数、库存总量、预警物料）之外，增加：

- **配件仓总值** = Σ(配件仓各物料 当前库存 × 加权成本)
- **成品仓总值** = Σ(成品仓各物料 当前库存 × 加权成本)

数据来源已具备，属于「后端已有、前端展示」的改动。

## 五、代为定下的细节（不同意随时改，否则按此实现）

| # | 项 | 默认方案 | 理由 |
|---|---|---|---|
| 1 | 提交后库存**超卖**风险 | 提交时**校验可用量但不锁定**；仓管确认、拣货完成时**各再校验一次**，不足则提示并允许驳回 | 与你「真实出库才扣」的拍板一致；加锁会让可用量口径变复杂，先不上 |
| 2 | 驳回怎么走 | 回到领料员手里，**可改可撤**（复用现有 `rejected` 状态），撤销时若已扣库存则回补 | 沿用现有已实现的驳回链路，不新造 |
| 3 | 领料员确认收货的依据 | **明细逐项勾选核对**（不做扫码） | 扫码需要物料贴码 + 摄像头链路，超出本轮范围 |
| 4 | 采购收料发现不符 | 仓管**可退回给采购员**补充/更正，不直接作废 | 保留追责痕迹 |
| 5 | 出库类型 | 领料员**只做「领用」**；维修 / 销售 / 报废 / 赠品 / 调整 / 采购退货由仓管发起 | 与「领料员」职责定位一致 |
| 6 | 采购任务挂仓 | **任务本身带仓库**（领的料属于某个仓） | 入库时仓已确定，避免二次选择 |
| 7 | 老板两个总值口径 | **成本口径**（库存数 × 加权成本），**同时显示库存数量** | 数量是实感，金额是资产口径 |

> **已取消（2026-10-03 用户修正）**：采购任务**不填预期单价**。
> 仓管建任务只做三件事：选物料、填数量、可指定采购员；
> **单价一律由采购员在「采购录入」时填实际值**，不做预期/参考价，也不做超预算对比。

## 六、影响面提示

- 扣库存时机从「提交」挪到「收货」，牵动：出库单状态机、库存流水口径、驳回/撤销的回补逻辑、以及仓管员待办列表的判定条件。
- 领料流程从 2 态变 4 态，`storekeeper/pending.vue`「待确认」列表需要拆成「待确认 / 待拣货」两段。
- `outbound_orders.status` 是真 ENUM，加状态需要 `ALTER TABLE`（4 态 + rejected/cancelled 共 6 值），**上线时要注意历史单据状态映射**。
- 采购员权限变化后，现有 `purchase/submit.vue`（1260 行，完整购物车+入库录单）里的**入库部分要挪给仓管**，采购员侧只留「领取 + 采购录入」。
- `in` 角色取消后：测试身份 `dev_in` 要合并、入库模块 `roleRules` 要收紧、`utils/cloud.js` 与两处角色映射表要同步。
- 角色改名后，`utils/cloud.js` 里的测试身份文案、「我的」与首页的角色映射、以及首页功能列表的说明文字都要同步。

## 七、开工顺序（按依赖排，每阶段可独立验收）

| 阶段 | 内容 | 为什么这个顺序 | 验收方式 |

| **P0** | 角色合并与改名：`in`→`storekeeper`、`out`→领料员、测试账号同步 | 独立、低风险、肉眼可见；后续所有页面的角色判定都基于它 | 6 个测试账号登录，角色文案正确、无 `in` 残留 |

| **P2** | 领料线改造：4 态状态机 + 扣库存移到确认收货 + 待办拆分 + 接入通知 | 本轮最大改动，依赖 P1 | 全链路走一遍：领料员提交 → 仓管确认 → 拣货完成 → 领料员收消息 → 确认收货 → 库存才减 |
