## 二、我报的问题

### [P1] `purchase.entry` 会用采购员备注**静默覆盖**仓管建单时的备注
- **我做了什么**（原始请求）：
  ```
  POST /api/purchase  {"action":"entry","data":{"id":16,"purchase_channel":"淘宝",
    "external_no":"TB-R2-20261003","remark":"[V3-R2] 李娜第二轮正常采购录入",
    "items":[{"material_id":2104,"quantity":15,"unit_price":12.5}]}}
  ```
- **系统回了什么**（原始响应关键字段）：
  - entry 前 `detail {id:16}`：`"remark":"[V3-SETUP] 采购E-采购中"`，`"status":"taken"`
  - entry 后 `detail {id:16}`：`"remark":"[V3-R2] 李娜第二轮正常采购录入"`，`"status":"purchased"`，`"total_amount":187.5`
  - 结论：`remark` 字段**同一个列**，采购员录入时把仓管写的备注整条顶掉了。
- **我认为哪里不对**：仓管建单备注（如「采购E-采购中」「仓管发布采购-点火线圈B」这类作业指引/要求）是采购员**照单执行**的依据；采购员一录入，这条备注就永久消失，且**没有任何提示**。若仓管在备注里写了指定型号/供应商/价格上限，采购员填完单就再也看不到，事后也无从追查（我填的采购说明和仓管的要求混在一个字段里，互相覆盖）。**建议**：把「仓管建单备注」和「采购员录入备注」拆成两个字段（如 `create_remark` / `entry_remark`），或在 entry 时对已有 remark 追加/保留而不覆盖。
- **有没有证据**：**有原始请求 + 前后两次 detail 原始响应**（上）。

### [P2] `purchase.list` 的 `pageSize` 实际上限是 **50**，手册写的是 200；超出被静默截断、无任何提示
- **我做了什么**（原始请求）：`purchase.list` 分别传 `pageSize = 51/100/199/200/201/500/1000`。
- **系统回了什么**（原始响应关键字段，节选）：
  ```
  请求 pageSize=1000 → 回显 pageSize=50   返回条数=7  total=7
  请求 pageSize= 500 → 回显 pageSize=50   返回条数=7  total=7
  请求 pageSize= 201 → 回显 pageSize=50   返回条数=7  total=7
  请求 pageSize= 200 → 回显 pageSize=50   返回条数=7  total=7
  请求 pageSize=  51 → 回显 pageSize=50   返回条数=7  total=7
  请求 pageSize=  49 → 回显 pageSize=49   返回条数=7  total=7
  ```
- **我认为哪里不对**：手册（第 193 行起）明确说上限是 **200**，实际实现封顶在 **50**。当前测试库 task 只有 7 条，未暴露截断；但一旦任务数 > 50，前端按手册传 `pageSize:200` 也只能拿到 50 条，**又不报错、又不提示**，采购员会以为「任务就这么多」而漏单。手册与实现至少有一个是错的。**建议**：统一口径（改文档或改实现到 200），且超出上限时在响应里能看出来（如回显真实生效的 pageSize 已是 50，进一步可加 `truncated` 提示）。
- **有没有证据**：**有原始响应**（上）。「>50 条会静默丢失」为**推测**（当前数据量不足以直接复现截断，但回显 `pageSize=50` 已证明封顶值）。

### [P2] `purchase.entry` 传 `items:[]` 时，报错指向"某个物料的单价"，没提示"明细为空"
- **我做了什么**（原始请求）：
  ```
  POST /api/purchase  {"action":"entry","data":{"id":16,"purchase_channel":"淘宝",
    "external_no":"TB-R2","items":[]}}
  ```
- **系统回了什么**（原始响应）：`{"code":400,"data":null,"message":"请填写「【测试】空气滤芯 E型」的实际单价"}`
- **我认为哪里不对**：我根本没传任何明细，系统却报「请填写**【测试】空气滤芯 E型**的单价」——它会拿任务里的物料名来套，让人误以为「明细是有的、只是单价没填」，实际根因是 `items` 为空。**建议**：`items` 为空时直接提示「请至少填写一项采购明细」。
- **有没有证据**：**有原始响应**（上）。根因**推测**：服务端按任务明细合并入参、缺项即报「该项单价」所致。

### [P2] 分页参数写成下划线 `page_size` 会被**静默忽略**（已知坑，本轮复现确认）
- **我做了什么**（原始请求）：`purchase.list {page:1, page_size:100}`。
- **系统回了什么**：`code:0`，回显 `"pageSize":20`，返回 7 条（不传分页时也回显 20）——即下划线写法不报错、直接被忽略、回落默认 20。
- **我认为哪里不对**：手册已声明这是已知笔误坑，但**静默忽略**本身仍危险：前端或第三方按 `page_size` 传参时不会报错，永远只拿前 20 条，容易误判数据缺失。**建议**：识别到未匹配的分页参数名时至少告警，或对新旧写法都兼容。
- **有没有证据**：**有原始响应**（上）。

## 三、系统做对的地方

1. **重复领取被幂等拦住**：同一 `open` 任务连调两次 `take`，第二次返回 `data.duplicated=true` +「你已经领取过这项任务，请继续采购录入」，状态没有被重复变更；对已 taken 的 `id=16` 再 take 同样只提示、不报错。
2. **不存在的任务有明确 404**：`purchase.take {id:999999}` → `code:404`「采购任务不存在」，不会误当成功。
3. **单价校验很硬**：`unit_price` 填 `0`、负数、文字 `"abc"` **三种全被拒**，且文案点明原因「采购成本要按它计算」，能防住"入库成本变 0"。
4. **采购渠道白名单有效**：`taobao`（英文）报「只能是：淘宝 / 京东 / 线下 / 其他」，不传报「请选择购买方式」，中文四选一之外都被挡住。
5. **状态前置校验有效**：对未领取的 open 任务直接 `entry` → `code:403`「只有该任务的领取人可以录入采购信息」；对已 purchased 的任务重复 `entry` → `code:400`「请勿重复录入」，不会二次改价。
6. **采购员改不动数量（防篡改）**：entry 时把 `quantity` 从 20 改成 `9999`，系统静默按任务原值 20 落库，明细数量没被改，避免采购员随意放大采购量。
7. **越权一律 403**：`purchase.create` / `purchase.receive` / `outbound.confirm` / `user.list` 四个别人岗位的动作，采购员调用全部返回 `code:403`「无操作权限」，角色边界清晰。
8. **错填不污染数据**：B 环节 7 次错填全部被拒后回查 `id=16`，`status/channel/total_amount` 均保持原样，没有留下半条脏记录。
9. **备注入参最终被正常落库**：正常录入的 `remark=[V3-R2]…`、`external_no`、`total_amount=187.5` 都正确写入（唯一致命点是它覆盖了仓管的备注，见问题 1）。

## 五、我这个岗位愿不愿意继续用 / 敢不敢签字
