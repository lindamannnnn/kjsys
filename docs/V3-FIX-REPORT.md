## 二、P0：权限门（3 组 5 条）

### 拍板依据

报告末尾请你定的问题是「**管理员这个角色，老板能不能动？**」。本轮**按「立场 B」修**：
管理员是系统最高权限（能改权限、能作废已完成单据），老板不能碰。
理由：代码里本来就写了「只有管理员能授予管理员」（说明设计意图就是 B），而报告里老板自己也提了「改完不恢复，别人查日志才知道」这个具体担忧。
如你要改成「立场 A（老板能管管理员）」，需要改的是同一处 3 个函数，改回来成本很低——但「系统里永远至少有一个管理员」这条保护应当保留（它是防死锁的，与立场无关）。

| # | 问题 | 根因（源码级） | 改法 | 验证 |
|---|---|---|---|---|
| **P0-1** | 老板能**凭空造**管理员（`user.create` / `user.approve`） | 只有 `updateRole` 有「只有管理员能授予管理员」的校验，`create` 与 `approve` 没有 —— **三个入口只堵了一个** | 抽出 `assertCanGrantAdmin(ctx, roles)`，三个入口共用同一套规则（以后再加入口不会再漏） | A1 老板 `create{roles:["admin"]}` → **403**<br>A2 老板 `approve{roles:["admin"]}` → **403**<br>A2b 管理员审核通过普通角色 → **0**（没误伤） |
| **P0-2** | 老板能**剥夺**管理员的角色、也能**禁用**管理员 | ① `updateRole` 只拦「授予自己不具备的 admin」，对「剥夺别人的 admin」零校验<br>② `setStatus` 连「不能禁用管理员」都没写 | 新增 `assertCanRevokeAdmin()`；`disable` 增加「非管理员不能禁用管理员」 | A3 老板降级 admin → **403**<br>A4 老板禁用 admin → **403** |
| **P0-3** | 管理员**能把自己降级** → 系统再无管理员，**且无法自救**（死锁） | `isLastActiveManager` 的查询条件把 **boss 也算作管理账号**，于是「唯一管理员要降级」被判定为「系统里还有 boss，安全」→ 放行 | 拆出 `isLastActiveAdmin()`，**只认 admin**；`updateRole` / `setStatus` 改用它，保证系统里永远至少有一个 admin | A8 **SQL 对照实验**：同一场景下<br>新条件 = **0**（判定为唯一管理员 → 保护触发）<br>旧条件 = **2**（判定还有别人 → 保护失效） |

### 为什么 P0-3 只能做源码级 + SQL 对照验证

**一旦实际复现，系统里就没有 admin 了**，而「授予 admin」又要求操作者自己是 admin —— 死锁。
上一轮两位岗位 Agent 实测时，都是**靠 P0-1 那个漏洞再造一个 admin 才恢复回来的**，这恰好说明两条漏洞叠加的威力。
因此本轮用「同一场景、两套查询条件」的对照实验证明根因已修（新条件判定为唯一管理员 → 保护会触发），而不是真把管理员降级掉。

## 四、报告之外新发现并修掉的 3 项

### 4.1 预警口径还有 **4 处**没统一（同类问题的完整闭环）

上一轮只统一了「看板 / 预警明细 / 按仓汇总」三处，本轮 grep 全库后发现还有 **4 处**各写一套、写法还不一致：

| 位置 | 原写法 | 问题 |
|---|---|---|
| `stats.stockList`（物料列表「只看预警」） | `warning_stock > 0 AND current_stock **<=** warning_stock` | 比看板多算「刚好等于阈值」的料 |
| `material.list`（物料档案「只看预警」） | 同上（`<=`） | 同上 |
| `warehouse.list`（仓库汇总的预警数） | `current_stock <= warning_stock` | 连「必须设了预警线」都没有 |
| `jobs/index.js`（每日预警扫描定时任务） | 同上 | 同上 |

**改法**：把口径抽成唯一出处 `src/services/warning.js`（`WARNING_COND` / `WARNING_COND_INCLUDE_IDLE`），
**6 处全部改为引用同一个常量**。以后不可能再各自漂移。

**验证**（D1）：看板 = 预警明细 = 物料列表 = 仓库汇总 = **31**，四个数字完全一致。

### 4.2 预警接口的「零库存数」只统计当前页

`stats.warning` 的 `out_of_stock` 原来是 `rows.filter(r => current_stock <= 0).length`，
而 `rows` **只有当前页** → `pageSize=1` 时最多显示 1，还会随翻页变化，与看板对不上。

**改法**：改为 SQL 全量 `COUNT(*)`。
**验证**（D2）：`pageSize=1` 与 `pageSize=200` 返回的 `out_of_stock` 相同。

### 4.3 审计日志缺操作者角色

老板点名的一条：「`updateRole / disable / enable / create / resetPassword` 写日志时没传 `role`，
日志里危险操作的 `role` 全是空串，只能靠 `user_name` 判身份」。

**改法**：`user.js` 5 处手工补齐；`outbound.js` / `inbound.js` 共 7 处用规整模式批量补齐；改完逐项核对。
**核对结果**：`writeOpLog` 调用 **16 处全部带 role，0 处遗漏**（`auth` 的登录类日志不记角色属正常——登录前/失败时还没有角色）。
