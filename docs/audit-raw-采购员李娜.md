## 二、我遇到的问题

### [P0] 撤销一张入库单，数量退回来了，加权成本没退回来——账对不平

- **现象**：我在「采购详情」里把一张当天未确认的入库单 **IN-20261001-013（机油滤芯 D型 ×10 @100）** 撤了。页面提示"作废成功，库存已回退"。我去查库存：**数量**从 111 退回到了 101，是对的；但**加权成本**还停在 17.8715，没有回到入库前的 9.74。等于这 10 个货"人走了、账没走"，剩下 101 个的账面价值被虚抬了 821.28 元。
- **原始请求**（提交）：
  `{"action":"submit","data":{"type":"purchase","supplier":"【测试】顺德紧固件厂","supplier_id":48,"remark":"采购审核-撤销成本回退测试","warehouse_id":1,"items":[{"material_id":1956,"material_name":"【测试】机油滤芯 D型","material_spec":"TEST-OIL-D","unit":"个","quantity":10,"unit_price":100}]}}`
- **原始响应**（提交）：`{"code":0,"data":{"_id":182,"order_no":"IN-20261001-013","total_price":1000},"message":"入库单提交成功"}`
  → 提交后成本 9.74 → 17.8715（`material.detail` 实测 `avg_cost:17.8715`）
- **原始请求**（撤销）：`{"action":"cancel","data":{"id":182,"reason":"撤销成本回退测试"}}`
- **原始响应**（撤销）：`{"code":0,"data":null,"message":"作废成功，库存已回退"}`
  → 撤销后 `material.detail`：`current_stock:101`，`avg_cost:17.8715`（**没变**）
- **库存流水**（`stats.stockFlow`，material_id=1956）：
  ```
  {"change_type":"inbound_cancel","change_quantity":-10,"before_stock":111,"after_stock":101,"order_no":"IN-20261001-013",...}
  {"change_type":"inbound","change_quantity":10,"before_stock":101,"after_stock":111,"order_no":"IN-20261001-013",...}
  ```
  即撤销只补了一条"退回数量"的流水，**没有任何一条把价值/成本退回来的记录**。
- **预期**：撤销一笔入库，数量和价值要一起回退，成本回到入库前的 9.74。理由：系统连"改价"都会自动重算成本并写"改价成本修正"流水，撤销一笔整单更应该回退。按加权平均，正确账面价值 = 9.74×101 = **983.74**。
- **独立复查**：库存流水 1956 的 `net_quantity = 101` = 当前库存 101（**数量账是平的**）；但当前 `101 × 17.8715 = 1805.02`，对比正确值 `983.74`，**差 821.28 元**。另外我作为采购员没有任何办法把这个被带歪的成本改回去（改价只对未确认单按"金额差额"倒推，算回来会得到负单价被拒），只能干看着。
- **证据强度**：**实证**

### [P1] "防重复提交"是摆设：前端每次请求都换一个新幂等键

- **现象**：手册说带相同 `client_request_id` 只会生效一次。我验证了——**只要两次调用带的是同一个键，确实只生效一次**。但问题在于**前端根本不会重复用同一个键**：`miniprogram/src/utils/cloud.js:109` 每次 `callCloud` 都 `const client_request_id = \`${Date.now()}-${Math.random()...}\``。所以我"手抖点两次"，是两次不同键的请求 = 两张单。
- **原始请求**（第 1 次，不带 client_request_id）：
  `{"action":"submit","data":{"type":"purchase","supplier":"【测试】顺德紧固件厂","supplier_id":48,"remark":"采购审核-手抖重复提交","warehouse_id":1,"items":[{"material_id":1956,...,"quantity":1,"unit_price":9.74}]}}`
- **原始响应**：`{"code":0,"data":{"_id":183,"order_no":"IN-20261001-014","total_price":9.74},"message":"入库单提交成功"}`
- **原始请求**（第 2 次，内容一模一样，仍不带键）：同上
- **原始响应**：`{"code":0,"data":{"_id":184,"order_no":"IN-20261001-015","total_price":9.74},"message":"入库单提交成功"}`
  → **生成了两张单，库存 101 → 103（重复加了 2 个）**
- **对照**：带相同键的两次调用，第 2 次返回 `{"code":0,"data":{"_id":180,"order_no":"IN-20261001-011","duplicated":true},"message":"该入库单已提交（单号 IN-20261001-011），请勿重复操作"}`，库存不加。**说明后端能力是有的，是前端没用上。**
- **预期**：同一笔业务（同物料、同数量、同供应商、几秒内）应只生效一次；至少前端要用同一个键，网络重试/多端点"提交"才不会重复入库。
- **独立复查**：`material.detail` 1956 库存由 101 变 103，两张单 `IN-20261001-014`、`IN-20261001-015` 都在列表里躺着。
- **证据强度**：**实证**（接口行为）+ **实证**（源码 `cloud.js:109`）

### [P1] 月底要的对账单，系统给不全（数量能拼、钱和成本对不平）

- **现象**：我想回答三个问题——"这个月买了多少 / 花了多少钱 / 现在还剩多少"，结果：
  1. **没有采购员能看的汇总**：`stats.overview`（有"今日入库金额/数量"）对采购员返回 **403 无操作权限**；`stats.materialRank` 也 403。
  2. **入库流水没有金额**：`stats.stockFlow` 每条只有 `change_quantity`（数量）和 `before/after_stock`，**没有单价、没有金额**，我无法从流水还原"某料号本月入库花了多少"。
  3. **采购历史只能自己加**：`inbound.list` 有日期/状态筛选，但不给合计；导出 CSV 只有**主单**金额，没有按料号的数量/单价。
- **原始请求**：`{"action":"overview","data":{}}` → **原始响应**：`{"code":403,"data":null,"message":"无操作权限"}`
- **原始请求**：`{"action":"stockFlow","data":{"material_id":1956,"page":1,"pageSize":50}}` → 返回的每条记录字段只有 `change_type / change_quantity / before_stock / after_stock / order_no / operator_name ...`，**无 unit_price / amount**。
- **实测口径陷阱**：直接对 `inbound.list` 求和会把**已作废**的单也算进去——
  `status=(全部) → 14 单 金额合计 ¥11736.02`，其中 `已作废 7 单 ¥1092.80` 是虚的；只有 `1149.22(pending)+9494.00(confirmed)=10643.22` 是有效的。不筛状态就会虚增。
- **预期**：采购员能一键得到"本月入库汇总（按料号：期初/入库量/入库金额/期末库存/加权成本）"，且作废单自动剔除；库存流水能带出金额维度。
- **独立复查**：见 P0-1，连"还剩多少值多少钱"这一项都因为撤销不回退成本而不可信。
- **证据强度**：**实证**

## 三、设计建议（不算缺陷，但影响我用得顺不顺）

1. **撤销入库单要能连成本一起回退**（P0-1 的根因）。或者干脆禁止对已影响成本的入库单做"撤销"，改成"红冲"一张负数入库单，让流水里能看见"这笔钱退了"。
2. **已确认单采购员不能改价**——手册说这是设计（只有老板/管理员能改已确认单），我认。但现实里"仓管确认后才发现价错了"太常见了，每次都要去喊老板不现实。建议给采购一个**当天限时的自助改价**或**"改价申请"**入口。
3. **入库单价加"异常价"预警**（比如超过该料近 30 天均价 3 倍就弹确认）。
4. **供应商设为必填**，`supplier_id` 校验存在性。
5. **前端统一复用幂等键**：手动点"提交"时生成一次 `client_request_id` 并随重试沿用（`cloud.js:109` 现在是每次都新生成，等于没有幂等）。
6. **库存流水加"单价/金额"列**；给采购员一个**"本月入库汇总"卡片**（按料号：入库量、入库金额、期末库存、加权成本），并自动剔除作废单。
7. **采购历史导出加按料号的量价明细**（现在只有主单金额）。
8. **历史关键词支持备注搜索**。

## 四、我这个岗位愿不愿意继续用 / 敢不敢签字

**分场景表态，但有一句话先说死：我不敢拿它的成本数据去对账。**

- **日常报采购、看还剩多少、查单号、新建供应商、按编号搜料**：**愿意用**。第 1 轮那一整套动作是真的顺，编号精确搜索、细分类筛选、加权成本算法都对，比我现在拿本子记强。
- **当"采购台账 / 月底对账单"**：**不敢签字，暂时不愿意用**。三条硬伤：
  1. **撤销一张入库单，数量退了、钱没退**（P0-1）。库存价值当场虚高 821.28 元，而我作为采购员没有任何自助手段修回来。财务拿这个成本去结转，就是错账。
  2. **拿不出"本月采购汇总"**（P1-4）：采购员没有汇总接口，流水没有金额，导出只有主单金额，还得自己筛作废单——一份能签字的对账单，系统给不出来。
  3. **防重复提交形同虚设**（P1-1）：手抖两下就是两张单、库存加两次，月底对账又得靠人肉找差异。

**结论**：系统的"单据流转、库存加减、权限隔离"这几条主干我觉得是靠谱的，可以继续用来**跑采购作业**；但**成本/金额这条账，在 P0-1 修好之前，我不会拿它当采购台账去对账、也不签字**。修好撤销回退成本 + 补一个月度汇总，我马上改口。
