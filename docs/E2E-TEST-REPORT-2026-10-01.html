二、发现的问题

严重 AUTHZ-01：未审核用户能读取公司经营数据

现象：任何人扫码进入小程序，系统会自动为其建档（状态「待审核」、无角色）。这个本不该看到任何业务数据的人，实际上可以直接拉取：

material.list        物料档案（含编码、规格、库存、成本）
material.categories  物料分类
supplier.list        供应商列表
supplier.search      供应商搜索
warehouse.list       仓库列表
inbound.list         入库单列表
outbound.list        出库单列表
check.list           盘点单列表

原因：server/src/app.js 的登录校验只拦了 status === 'disabled'，没有拦 status === 'pending'；而上述 8 个查询接口没有配置角色要求，于是两道门都放行了。

影响：物料档案、供应商名单、单据流水属于公司经营信息。虽然写入操作仍被角色校验拦住（已验证），但只读数据已经泄露。

修复建议：在 app.js 的登录校验里补上 pending 拦截，并把登录/注册/查自己信息几个接口加入白名单：

// server/src/app.js 登录校验处
const PENDING_EXEMPT = ['login', 'register', 'getUserInfo', 'updateProfile', 'myLogs']
if (!isPublic && ctx.user.status === 'pending' && !PENDING_EXEMPT.includes(action)) {
  return res.json(fail(403, '账号正在审核中，请联系管理员开通权限'))
}

修复后需要同步确认前端：待审核用户进入首页时应当被引导到「等待审核」提示，而不是空白报错页。

轻微 AUTHZ-02：被禁用的员工仍能登录成功

现象：管理员把某人禁用后，该员工打开小程序依然能登录成功、拿到自己的角色列表和令牌，只是接下来每次调用接口才会被拒绝（403「账号已被禁用」）。

影响：数据没有泄露（接口层拦住了，已验证），但体验很差：员工能看到完整的功能界面，点什么都报错，还会来问「为什么用不了」。

修复建议：在 auth.login 里查到用户后，若 status === 'disabled' 就直接返回拒绝，不签发令牌。

轻微 UX-01：越权打开页面时显示「0」而不是「无权限」

现象：出库员手动输入老板看板的网址，接口正确返回 403，但界面上显示的是一排「0」（今日出库单数 0、库存总量 0……），看起来像「公司真的一单都没有」。

影响：用户会误判成数据丢失，也可能反复来问。属于误导性展示。

修复建议：接口返回 403 时，页面展示「暂无权限查看，请联系管理员」的提示态，而不是把空值当数据渲染。

开发环境 DEV-01：5173 端口被两个服务抢占

现象：本机 localhost:5173 打开的是小程序首页，而 127.0.0.1:5173 打开的才是后台管理。localhost 解析到 IPv6 后被小程序的 dev server 接管，后台的 dev server 只绑在 IPv4 上。

影响：不影响线上，但会导致「明明改了后台代码却看不到效果」这类排查困难。本次测试第一遍就被它骗过——报告显示后台 18 个页面全部「正常」，实际上一个后台页面都没打开。

修复建议：给两个 dev server 固定不同端口（例如后台 5188、小程序 5199），或在文档里标注必须用 127.0.0.1。

代码整洁 DEAD-01：后台装了图表库但一个图表都没用

现象：admin/package.json 引入了 echarts 与 vue-echarts，但 18 个页面里没有任何一页使用图表，统计全部用表格呈现。

影响：仅是打包体积与依赖维护成本，不影响功能。若老板希望看板有折线图/柱状图，这里是可以直接用的。
