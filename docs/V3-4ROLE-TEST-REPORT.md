# 盛龙 ERP · 第三轮多岗位真实使用者测试报告（V3）

> **本轮与前两轮的根本区别**：全部改用 **「模拟微信身份」登录**（服务端 `dev_openid` 直通，不接真实微信），
> 上线时才换成真实微信登录。因此每个岗位都有 `openid`，**消息通知这类按 openid 投递的链路第一次被真实测到**。
>
> 测试对象：本机 `http://127.0.0.1:3000`（真实服务 + 真实数据库）
> 测试时间：2026-10-03
> 测试方式：5 个岗位 Agent × 3 轮，同时在线，互不串通

---

## 一、测试方法（含必须声明的局限）

### 怎么测的

5 个「岗位 Agent」扮演真实使用者，**同时在线**跑 3 轮，每轮聚焦不同目标：

| 轮次 | 目标 | 说明 |
|---|---|---|
| 第 1 轮 | **正常作业** | 每个岗位按自己真实的工作路径把活干完（不是随便挑接口打） |
| 第 2 轮 | **做错事与异常** | 故意乱填、超量、重复提交、并发抢单、撤销各状态的单 |
| 第 3 轮 | **权限边界 + 追责对账** | 逐个 action 试越权；再用库存流水把账一笔笔还原 |

5 个岗位：**领料员张三**（`dev_out`）、**仓管员赵六**（`dev_sk`，管配件仓+成品仓）、
**采购员李娜**（`dev_purchase`）、**老板王总**（`dev_boss`）、**后台管理员**（`admin`，管后台管理系统）。

每个 Agent 都被要求：
- 只能碰 `【测试】` 前缀的物料，单据 `remark` 必须带轮次标记
- **每条问题必须附「原始请求 + 原始响应」**，没证据的只能标「推测」
- 看到状态与预期不符时**先回查确认**（因为其他 4 个岗位正在同时操作），不许上来就报 bug
- 最后必须回答「**我这个岗位愿不愿意继续用 / 敢不敢签字**」

### 局限（必须声明，否则结论会被误读）

1. **登录方式是模拟身份，不是真实微信**。真实微信登录的链路（`code2session`、`WX_SECRET`）
   本轮**没有测**，需要上线前单独验。
2. 5 个 Agent 共享同一个系统实例，**存在相互干扰**：一个人的操作会改变另一个人看到的状态。
   凡属这类，本报告一律归入「环境噪声」，不计为缺陷。
3. 本轮**没有做浏览器 UI 验证**（页面白屏、按钮无响应、样式错位这类需要真实浏览器才能发现的问题，
   本轮未覆盖）。接口层测得的是「后端逻辑」和「前端契约」，不等价于「界面好用」。
4. 第 1 轮的测试手册有 **2 处字段名写错**（见第七节），已在本轮内修正——出错的是我的手册，不是系统。

## 二、结论摘要

| 级别 | 数量 | 说明 |
|---|---|---|
| **P0** | **3 组（展开 5 条）** | 全部集中在「谁能当管理员」这一件事上，已全部独立复核成立 |
| **P1** | **10 条** | 数据会算错 / 权限不一致 / 审计留痕缺口 |
| **P2** | 12 条 | 体验与文案类，未逐条处理 |
| 假问题 | 5 条 | 已排除，见第七节 |

**各岗位表态：**

| 岗位 | 愿不愿意继续用 | 卡在哪 |
|---|---|---|
| 领料员张三 | 愿意 | 首页把「成品仓」露给他，点进去又被拒（已修） |
| 仓管员赵六 | 愿意用；**盘点追责不敢签字** | 老板建的盘点单，列表看得见、详情点不开 |
| 采购员李娜 | 愿意用；**月底金额账暂时不签** | 建单备注会被采购录入抹掉；金额带 4 位小数 |
| 老板王总 | **不敢签** | 权限边界有洞：老板能换掉/造出管理员 |
| 后台管理员 | 一致性敢签，管理权限不签 | 「谁能当管理员」这道门是漏的 |

**一句话总结**：
**数据这一层已经站得住了**（三处独立对账全部零差异、库存流水能一笔笔还原），
**但权限这一层有一道门是漏的** —— 系统里「管理员」这个角色可以被一个非管理员凭空造出来、也可以被剥夺掉，
而现有的保护逻辑把「老板」和「管理员」当成一回事，导致唯一的管理员被摘掉后**系统无法自救**。

## 四、你报的「后台成品仓和小程序不同步」——最终结论

**3 轮独立验证，结论一致：数据层和接口层完全同步，问题在展示层（已修）。**

| 层 | 怎么验的 | 结果 |
|---|---|---|
| 数据层 | admin token 与老板 token 各拉一次，**逐 ID 比对** `current_stock`/`avg_cost`/`warning_stock` | 配件仓 1770 条、成品仓 149 条，**不一致 0 条**（3 轮都是 0） |
| 接口层 | 抓两端实际调的接口 | 同一套 `/api/*`、同一个 `warehouse_id=2`，**不是两套数据源** |
| 展示层 | 读源码 + grep 构建产物 + 查响应头 | 4 处不同步 → **已全部修复**（见下） |

**展示层当时的问题（上一轮已修，本轮验证修复有效）：**

1. 后台构建产物陈旧（落后源码两天，且残留已废弃的「入库员」角色）→ 已重建
2. 后台看板的单据状态文案缺 V2 三态（同一张单小程序显示「待收货」、后台显示英文 `receiving`）→ 已补
3. 后台没有「消息中心」页面（接口封装写好了但没有页面调用它）→ 已新建
4. 静态托管把 `index.html` 也缓存 1 天 + SPA 兜底对任何缺失路径都返回 HTML
   → 发版后浏览器用旧首页 → 引到已删除的旧 hash 文件 → 服务端把 HTML 当 JS 回 → **白屏或一直看到旧后台** → 已修

**本轮验证**：后台产物能搜到 `采购任务`/`消息中心`/`待拣货`/`待收货`、搜不到废弃角色 `入库员`；
`/admin/index.html` 返回 `no-store`；请求不存在的静态资源返回 **404**（改之前是 200+HTML）；
`admin/src` 下 20 个页面与路由**零孤儿**。

> ⚠️ 部署时**必须把 `server/src/app.js` 的缓存策略修复一起上线**，否则用户仍会看到旧后台。

## 五、P0（全部已独立复核成立）

> 复核原则：**读源码确认根因 ＞ 实际发请求复现**。
> 会造成「不可恢复」后果的（比如把唯一管理员降级），**只做源码级根因确认，不实际复现**。

### P0-1　老板能凭空造出「管理员」

**现象**：用老板账号（`boss` 角色，**不是**管理员）直接创建一个角色为 `["admin"]` 的新账号 → **成功**。

**证据（我实测）**：
```
POST /api/user {action:"create", data:{username:"V3RECHECK_xxx", roles:["admin"]}} by dev_boss
→ {"code":0,"data":{"_id":57},"message":"账号创建成功"}
```

**根因**：`user.js` 的 `create` 与 `approve` 只做了 `roles.filter(r => VALID_ROLES.includes(r))` 白名单过滤，
**没有**「只有管理员才能授予管理员角色」的判断。而 `updateRole` 里有这道判断 —— 三个入口，只堵了一个。

**为什么危险**：管理员能作废已完成的单据、能改任何人的权限。等于任何人都能给自己开一扇后门。

---

### P0-2　老板能剥夺管理员的权限、也能禁用管理员

**现象**：老板可以把 `admin` 的角色改成 `["out"]`、也可以直接把 `admin` 禁用。

**根因（源码级，两处）**：
1. `user.js` 的 `updateRole` 只拦「**授予**自己不具备的 admin」，对「**剥夺**别人的 admin」没有任何校验
2. `middleware/auth.js:93` → `MANAGEMENT_ROLES = ['admin', 'boss']`
   `isLastActiveManager()` 认为 **boss 也算管理账号**，所以只要系统里还有任何一个 boss 角色账号，
   「唯一管理员要被摘掉」就被判定为安全 → 保护形同虚设

**说明**：这条我**没有实际复现**。因为把 admin 降级后系统里就再没有 admin 了，而「授予 admin」那一步是有边界的
——恢复路径只剩「利用 P0-1 那个漏洞再造一个 admin」。**一旦复现，能不能恢复取决于另一个漏洞还在不在**，
这个风险不该由测试来承担。两位岗位 Agent 已各自实测复现过一次（返回 `code=0`，角色真的被改），
并且**都是靠 P0-1 的漏洞才把 admin 恢复回来的** —— 这本身就说明了这两条漏洞的叠加威力。

---

### P0-3　管理员能把自己降级 → 系统再无管理员，且无法自救

**现象**：管理员把自己角色改成 `["boss"]` → 成功 → 系统里**没有任何 admin 角色**了。
此后「作废已完成单据」等仅限 admin 的操作，**没有任何人能做**；而用户管理里也没有入口能把自己改回 admin
（因为「授予 admin」需要自己是 admin —— 死锁）。

**根因**：同 P0-2 的第 2 点 ——`isLastActiveManager` 把 boss 也算管理账号，所以
「我把自己从 admin 降为 boss」被判定为「仍然是管理账号，安全」→ 放行。

**这一条无论产品上怎么定「老板大还是管理员大」，都是 bug** —— 它会让系统进入没有任何人能维护的状态。

---

> **需要你拍板的设计问题**：从权限表看，老板本来就有「用户管理」权限（`user.*` 对 `boss`/`admin` 都开放）。
> 所以真正要定的是：**「管理员」这个角色，老板能不能动？**
> - 立场 A：老板是最高决策者，能管管理员 → 那要修的是 P0-3（保证系统里永远至少有一个 admin），
>   P0-1/P0-2 属于「老板本来就有权」不算漏洞
> - 立场 B：管理员是系统最高权限，老板不能碰 → P0-1、P0-2、P0-3 三条都要修
>
> 我倾向 **B**：因为代码里已经写了「只有管理员能授予管理员」（说明设计意图就是 B），
> 而且「管理员」承载的是「作废已完成单据」这类**不可逆**的操作，不该由普通管理角色随意授予。

| 8 | **越权尝试不留痕** | 有人反复试着越权，日志里完全看不出来（6 次 403 → 日志 +0） | 后台管理员实测 |
| 9 | **主数据改动不留痕** | 物料档案、仓库、供应商资料、用户资料的修改**完全不写日志**，出了事查不到是谁改的 | 老板 + 后台管理员各自实测（`warehouse.upsert`/`material.upsert`/`user.update` 均 +0） |
| 10 | **老板收不到「盘点待审」通知** | 盘点提交后审批人不知道要去审；且没有任何消息类型面向老板 | 老板实测：空箱恒为 0，而同期仓管 51 条、领料员 3 条（管道本身是通的） |

## 七、已排除的假问题（不采信 Agent 原话的几条）

| 假问题 | 为什么不是真问题 |
|---|---|
| **「消息中心完全失效，收不到通知」**（前两轮的结论） | **本轮已证明：模拟身份下消息真实可达**。领料员收到了「你的领料单已拣货完成，请来收货」，采购员收到了「仓管已收料入库」。之前收不到是因为测试账号用**账号密码登录、`openid` 为空**，而消息按 openid 投递 —— 真实微信登录不受影响 |
| **「盘点账面数用建单快照，会凭空盘出盈亏」**（仓管第 1 轮报的 P1） | **误判**。源码 `check.js:375` 显示：提交时会**把账面数刷新为提交这一刻的实时库存**再算差异，并且当「建单时账面 ≠ 提交时账面」时会额外提示。仓管看到的 `book_stock=24 / current_stock=34` 只是详情页展示的建单快照，不是参与计算的数 |
| **「采购任务标着待收料、实际是采购中」** | 跨岗位干扰。当时仓管正在对同一批任务做收料/退回，状态在变。非缺陷 |
| **「历史单据『待确认』却有已扣库存标记」** | 是 10-01 迁移前的历史单，迁移脚本按设计把历史单标记为已扣（避免重复扣减）。属过渡数据，不是新缺陷 |
| **「管理员收不到站内消息」** | 后台账号没有 openid，`message.*` 返回空是**设计如此**（消息按人投递） |

**另有两处是我自己的手册写错（已修正，不是系统问题）：**
1. 手册写分页参数 `page_size`，实际是 **`pageSize`**（驼峰）。传下划线不报错、但被静默忽略 → 永远只回 20 条，
   会让测试员误判成「数据少了一半」。**V2 手册写的是对的，是我这轮写错了。**
2. 手册写盘点录入字段 `actual_quantity`，实际是 **`actual_stock`**。

## 八、系统做对的地方（防止整改时误伤）

**权限与边界**
1. 4 个岗位的权限矩阵实测：**该拦的一次都没漏**（领料员 31/31 被拒、采购员 31/31 被拒、仓管 15 项该拦全拦 / 22 项该放全放、越权对照 15/15 全 403）
2. 数据权限按可管仓库收敛：领料员看不到成品仓的单，跨仓操作 403
3. 不能取消自己的管理权限、不能摘掉最后一个管理账号（这两道护栏本身是对的，问题出在「老板被算作管理账号」这个前提上）

**资金与库存准确性（这是最要紧的）**
4. **库存时机完全正确**：出库「确认收货才扣」逐阶段验证通过；入库「提交即加库存」也逐阶段验证通过
5. **对账零差异**：多个岗位独立手算库存流水累加，全部等于当前库存；1919 个物料全量校验 0 偏差
6. **两端逐 ID 零差异**（3 轮各一次，配件仓 1770 + 成品仓 149）
7. **加权平均成本算得对**：手算 `(24×56+10×8.5)/34 = 42.0294` 与系统输出一致
8. **采购金额链闭合**：采购任务金额 → 收料自动生成的入库单金额，分毫不差（560 = 560）
9. 单据金额、分仓汇总、明细求和，逐层闭合

**安全与稳定性**
10. 幂等有效：重复提交、重复确认、重复领取都不会产生第二张单
11. 并发抢单用条件更新，不会两个人同时收料
12. 越权尝试、跨仓操作、不存在的 ID 都有明确中文报错，没有静默失败
13. 数据校验严的地方很严：数量必须正整数（0.5 个火花塞会被拒）、采购单价必须 > 0、购买方式白名单、驳回必须填原因
14. 越权尝试不会污染数据（做完错事，库里干干净净）
15. 后台产物与源码一致、无孤儿页面；静态托管缓存策略正确
